=== A. OWASP GenAI Security Project — LLM02:2025 Sensitive Information Disclosure ===

URL: https://genai.owasp.org/llmrisk/llm022025-sensitive-information-disclosure/
(Note: this risk was LLM06 in the original 2023/2024 OWASP LLM Top 10 ordering;
the 2025 revision renumbered it to LLM02. Both numbers appear across the
ecosystem depending on which version of the list a source cites.)

Verbatim description (confirmed on fetch):
  "Sensitive information can affect both the LLM and its application context.
  This includes personal identifiable information (PII), financial details,
  health records, confidential business data, security credentials, and
  legal documents."

Verbatim mitigation guidance (confirmed on two separate fetches, full paragraph):
  "To reduce this risk, LLM applications should perform adequate data
  sanitization to prevent user data from entering the training model.
  Application owners should also provide clear Terms of Use policies, allowing
  users to opt out of having their data included in the training model. Adding
  restrictions within the system prompt about data types that the LLM should
  return can provide mitigation against sensitive information disclosure.
  However, such restrictions may not always be honored and could be bypassed
  via prompt injection or other methods."

Significance: OWASP's own canonical mitigation list INCLUDES the system-prompt
restriction as one legitimate mitigation — but explicitly caveats it in the same
breath as unreliable/bypassable. It is offered as ONE item in a longer list
(data sanitization, redaction, DLP, access control), never as a standalone
control.

=== B. OWASP GenAI Security Project — LLM07:2025 System Prompt Leakage ===

URL: https://genai.owasp.org/llmrisk/llm072025-system-prompt-leakage/

Verbatim (confirmed on re-fetch, full sentence + surrounding context):
  "It's important to understand that the system prompt should not be
  considered a secret, nor should it be used as a security control.
  Accordingly, sensitive data such as credentials, connection strings, etc.
  should not be contained within the system prompt language."

Also (first fetch, not re-verified verbatim but consistent with the page's
framing):
  "disclosure of the system prompt itself does not present the real risk —
  the security risk lies with the underlying elements, whether that be
  sensitive information disclosure, system guardrails bypass, improper
  separation of privileges, etc."

Significance: This risk item is about the model's OWN system prompt/instructions
leaking — a different failure mode than a user-supplied document (e.g. an email)
containing a secret that the model echoes. It is NOT the same vulnerability as
our case. It is cited here only for the general principle it states about
prompt-level text ("should not be used as a security control") — which is a
directly transferable framing to any prompt-level rule, including a CLAUDE.md
instruction not to echo a value. The quote is NOT being used to claim OWASP
addressed our exact scenario.

=== C. DeepInspect — commentary on OWASP LLM06/LLM02 output-side controls ===

URL: https://www.deepinspect.ai/blog/owasp-llm06-sensitive-information-disclosure

Verbatim, disclosure path taxonomy:
  "Training-data leakage: The model emits content it memorized during
  training. The content can be PII (an email address, a phone number, a
  social security number that appeared in training data), proprietary text
  (a section of a copyrighted document, a verbatim passage from a
  confidential corpus), or system-level data (an API key, a configuration
  value that was inadvertently included in training)."

  "In-context leakage: The model emits content that was supplied to it
  during the current session through retrieval, tool output, or system
  prompt content."

  "Cross-tenant leakage: The model or the retrieval layer or the cache layer
  confuses one tenant's data with another's."

Verbatim, output-side gateway controls list (six items, condensed):
  1. "Per-identity PII classification on responses. The gateway runs the
     response through a classifier that flags PII patterns."
  2. "Per-identity content-class filtering" for unauthorized content categories
  3. "Schema-bound responses for tool-mediated outputs" to strip undeclared
     fields
  4. "Per-tenant scoping enforced at the gateway" as independent enforcement
  5. "Output-length and content-shape caps" to reduce bulk-exfiltration risk
  6. "Audit on every response with the classifier result" for forensic
     investigation

Significance: "In-context leakage" is the precise vocabulary term for the
4Shark scenario — the credential arrives via a tool call (email fetch), enters
context, and the model emits it. This is a third-party security vendor's
synthesis of OWASP's categories, not an OWASP-authored term itself — attributed
to DeepInspect, not to OWASP.

=== D. Simon Willison — "The lethal trifecta for AI agents" ===

URL: https://simonwillison.net/2025/Jun/16/the-lethal-trifecta/

Verbatim definition:
  "Access to your private data... Exposure to untrusted content... The
  ability to externally communicate" (three-part framing, exact wording
  per page: access to private data, exposure to untrusted content, ability
  to exfiltrate).

Verbatim on prompt-level defense reliability (confirmed on re-fetch, full
paragraph):
  "I said 'very good chance' because these systems are non-deterministic —
  which means they don't do exactly the same thing every time. There are
  ways to reduce the likelihood that the LLM will obey these instructions:
  you can try telling it not to in your own prompt, but how confident can
  you be that your protection will work every time? Especially given the
  infinite number of different ways that malicious instructions could be
  phrased."

Verbatim on the recommended alternative:
  "The only way to stay safe there is to avoid that lethal trifecta
  combination entirely."

Significance: Willison's trifecta is about an ADVERSARIAL prompt-injection
scenario (an attacker's untrusted content instructing the agent to exfiltrate
private data), which is a different threat model than 4Shark's case (a
well-intentioned client emails a password, the agent echoes it while
summarizing — no adversary, no injected instruction). It is cited here only
for his general, widely-cited statement on the UNRELIABILITY of "tell the
model not to" as a prompt-level defense — the mechanism argument transfers
even though the threat model differs. This distinction is preserved in
SPIKE.md.

=== E. protectai/llm-guard — Secrets scanner (input-side) ===

URL: https://github.com/protectai/llm-guard/blob/main/docs/input_scanners/secrets.md

Verbatim:
  "This scanner diligently examines user inputs, ensuring that they don't
  carry any secrets before they are processed by the language model."

Verbatim, detection engine:
  Uses the detect-secrets library (built by Yelp) to detect API tokens,
  private keys, and high-entropy strings.

Documentation classification: input-side scanner — runs BEFORE the prompt
reaches the model, not on the model's generated output.

=== F. protectai/llm-guard — Sensitive scanner (output-side) ===

URL: https://protectai.github.io/llm-guard/output_scanners/sensitive/

Verbatim:
  "serves as your digital vanguard, ensuring that the language model's
  output is purged of Personally Identifiable Information (PII) and other
  sensitive data"

Detects/configures: PII entity types (PERSON, EMAIL given as examples),
extensible via regex. Uses "mechanisms from the Anonymize scanner." Operates
as a downstream filter on the completed model response.

Significance: LLM Guard's own documentation splits secrets detection
(input-side only) from sensitive-data/PII detection (output-side). Nothing
in LLM Guard's own docs describes the Secrets scanner (detect-secrets/Yelp
engine — the component actually built for credential-shaped strings) as
running on OUTPUT. The output-side "Sensitive" scanner is described in terms
of PII, not credentials/API keys specifically, though its regex is
user-extensible.
