Comparison — Command-Form Redirect Hook Options

Four candidate designs for a mechanism that intercepts a wrong-shape Bash command and either rewrites it into an already-approved canonical form or blocks it with the exact correction. No option is marked recommended — the engineer decides.

Generated 2026-07-16 — spike: command-form-redirect-hook

Option A — Generalized table-driven redirect

One script, `redirect-bash-form.sh`, with an internal rewrite table covering every catalog entry (§ SPIKE.md Finding C).

Pros

  • +One file to read/maintain; the catalog IS the code
  • +New rewrite = one new case, no new hook registration in settings.json
  • +Consistent conservative-parsing discipline enforced once, not per-script

Cons

  • −A bug in shared parsing logic risks every rewrite shape at once
  • −Larger single script is harder to reason about per-shape than today's small, single-purpose files
  • −Diverges from the existing pattern (`redirect-terraform.sh`, `redirect-ecs-scale.sh` are already one-per-tool)
Deep dive

Each existing redirect hook (terraform, ecs-scale) is independently conservative-parsing and independently deferring. A generalized version needs a dispatch layer that tries each rewrite rule in turn and defers if none match — functionally similar to today's per-script `exit 0` defer chains, just co-located. The maintenance question is whether one file growing over time (as more catalog entries are added) becomes its own review burden, mirroring the concern the Documentation Loading Model raises about a single CLAUDE.md growing past a size threshold.

Effort: MRisk: Medium (shared-logic blast radius)

Option B — N per-tool redirects (continue today's pattern)

One script per wrong-shape family, exactly like `redirect-terraform.sh` and `redirect-ecs-scale.sh` today; add `redirect-hubflow.sh`, `redirect-multiline-join.sh`, etc. as separate files.

Pros

  • +Proven pattern — two working examples in production today
  • +A bug in one redirect cannot affect another's parsing
  • +Each script's conservative-defer contract is independently auditable

Cons

  • −Every new shape is a new hook registration in settings.json's `PreToolUse` array (already 15+ entries)
  • −Duplicated boilerplate (hook_input parsing, tool_name check, quote/compound-command defer guards) across N files
  • −All N run in parallel per Finding A3 — more scripts matched to the same `Bash` event means more parallel processes per command, though each is cheap and short-lived
Effort: S per shape, cumulative M–LRisk: Low per-shape

Option C — Block-and-tell only (no silent rewrite)

Extend `validate-bash-command.sh`'s existing block messages so every wrong-shape block names the EXACT corrected command to retry — no `updatedInput`, ever.

Pros

  • +Zero risk of the mechanical hazard in Finding A2/A3 (no rewrite ever bypasses a block via parallel-hook races)
  • +No new mechanism — pure content improvement to an already-audited script
  • +Every corrective message already follows this shape today (see `validate-bash-command.sh` throughout)

Cons

  • −Does not solve the engineer's stated complaint — the agent must still notice the block, read the message, and retype the command itself; the "the mechanism enforces it" goal (spike question) is not met
  • −Costs one wasted turn per wrong-shape attempt, same as today
  • −Relies on the agent reliably reading and acting on stderr feedback — the exact discipline gap the engineer's complaint names
Effort: SRisk: Lowest

Option D — Rewrite-and-announce

Same mechanism as A or B (auto-rewrite via `updatedInput`), but every rewrite ALSO emits a visible `additionalContext` note ("rewrote X → Y because Z") so the correction is never fully silent even though it still auto-approves.

Pros

  • +Solves the engineer's stated goal (the mechanism enforces the canonical form) while keeping the correction visible for audit
  • +`additionalContext` is a documented, already-used field (Finding A1) — no new mechanism, just an added field on existing redirect hooks
  • +Builds a visible trail if a rewrite is ever wrong — easier to catch in review than a fully silent one

Cons

  • −Still carries the mechanical hazard in Finding A2/A3 for any NEW shape moved from block to rewrite (the parallel-hook precedence question is unresolved by official docs)
  • −`additionalContext` is capped at 10,000 characters combined with every other hook's output on the same event (Finding A4) — a verbose per-rewrite announcement competes for that budget
  • −Adds a step (crafting the announcement) to every redirect script, whether A or B is chosen underneath
Effort: S increment over A/BRisk: Same as underlying A/B

Decision criteria for the engineer (not a recommendation)

  • Does the goal require the mechanism to actually change what runs (A/B/D), or is a reliably-worded block-and-retry acceptable (C)? This is the crux of the engineer's original complaint — see SPIKE.md § Investigation question.
  • Is the mechanical uncertainty in Finding A2/A3 (undocumented precedence between a parallel `updatedInput`-allow hook and an existing `exit 2` block on the SAME shape) acceptable to build on without an empirical test first, or does it need to be resolved before any A/B/D work begins?
  • Is per-shape file proliferation (B) or single-file consolidation (A) the better fit for how `dot-claude`'s script directory is reviewed and PR'd today?
  • Is a visible announcement (D) worth the added `additionalContext` budget pressure and per-script effort, or is a fully silent rewrite (A/B) acceptable given the redirect only ever targets FORM problems, never SAFETY ones (§ Finding D)?
