# Identifier handling on records

The integrator generates the customer-side identifier that the 4Shark API expects to receive in payloads. The rule is two-line:

```ruby
def user_id_from(id)
  if normalized?
    "4sk_#{id}"
  else
    id
  end
end
```

That's it. The whole thing. This chapter covers why two modes is enough and why every other variant the codebase used to carry is gone.

## The rule

Every Resource the integrator pushes carries a customer-side identifier — a string that uniquely identifies the entity within the customer's domain. The 4Shark API uses this identifier as the external id of the record, the one the platform stores alongside its internal numeric id (Deliverable 1, Chapter A covers the platform side of identity translation).

The integrator's job is to pick that string. The choice is determined by the Source the data came from:

- **Normalized Source** — the Source provides a stable per-row `id` column (the primary key of the normalized schema). The integrator prefixes it with `'4sk_'` and emits, e.g., `'4sk_42'`. The prefix is a marker that the identifier was generated by 4Shark's normalized contract, not by an upstream system the customer uses.
- **Non-normalized Source** (custom DB query, ApiSource, future FTP/etc.) — the Source emits whatever identifier the customer's upstream system already uses. The integrator passes it through unchanged.

`Source#user_id_from(id)` is the single entrypoint. Every Resource subclass's `request_body_for(import)` invokes it for User-bearing fields; every Loader Consumer that resolves a user reference invokes it. There is no second path.

## Why a prefix on normalized sources

The normalized contract is **4Shark's schema**, populated by the customer's MIS team from their upstream systems. The `id` column in `fsk_users` is a synthetic primary key the schema imposes — it doesn't come from the customer's CRM, payroll, or HR system. It exists because the integrator needs a stable per-row identifier, and the customer's existing identifiers (badge number, CPF, employee code) often aren't unique across all subsidiaries or all source systems.

Prefixing with `'4sk_'` makes two things true:

1. **The identifier won't collide with anything the customer's other systems might emit.** A customer that later integrates a SaaS API alongside their normalized DB will see `sfdc-EMP-001` from Salesforce and `4sk_42` from the normalized DB. The two namespaces don't overlap. (Chapter 8 covers `IdentifierPrefixerTransformer`, which adds the per-API-source prefix on the transform side.)
2. **The identifier is self-describing.** Anyone debugging the 4Shark side, looking at a User record with `external_id = '4sk_42'`, knows at a glance that the user came in through the normalized integration channel. They know which integrator produced it, which Source within that integrator, and where to start looking if something is wrong.

The cost is a 4-character prefix on every identifier. The cost is invisible — the customer never sees these strings; they appear only in API payloads and on platform-side records.

## Why no prefix on non-normalized sources

When the customer's source system already has stable identifiers (Salesforce contact IDs, an existing internal payroll system that tracks employees by ID, a custom-shaped DB the customer maintains), those identifiers **are** the customer's truth. The integrator's job is to faithfully forward them, not to wrap them.

Prefixing a custom Source's identifier would break the customer's mental model. If their HR system's user ID is `EMP-001` and the 4Shark platform stores them as `'4sk_EMP-001'`, the customer trying to debug "why is EMP-001's commission wrong?" has to know to add the prefix when querying our side. That's friction with no benefit — the customer's identifier is already unique in their world, and the platform stores it as-is.

The pass-through mode also lets multiple ApiSources coexist without name collisions — the `IdentifierPrefixerTransformer` (Chapter 8) handles that case at the transformation layer with a per-Source 4-character prefix that is independent of the `4sk_` mechanism.

## The history: why this used to be three modes

Before PR #2120, the same logic lived on `Import#identifier` and carried three modes:

1. **Per-Source `identifier_prefix`** — each Source could carry its own arbitrary prefix string (`'sfdc_'`, `'tkmb_'`, `'crm_'`, etc.). The Source documents accumulated whatever per-customer prefix decisions had been made.
2. **`managed_integration?` mode** — a global flag on `ApplicationConfiguration` that, when true, said "this integrator is managed by 4Shark, don't apply any prefix". The "managed" customers were the ones using the normalized contract; the assumption was that the normalized schema's identifiers were already 4Shark's, so adding a prefix would be redundant.
3. **`'4sk_'` default** — a hardcoded fallback for everything else.

The three modes carried two underlying confusions:

- **Mode 1 was solving an API-side identity problem at the wrong layer.** The per-Source prefix was used to disambiguate identifiers across multiple Sources within a customer; that's a transformation concern (one record's `external_id` field), not a Source-property concern. Moving it to a Transformer (`IdentifierPrefixerTransformer`) made it composable with the rest of the mapping pipeline.
- **Mode 2 had the polarity inverted.** The `managed` (normalized) flow is precisely the one that needs the prefix — the synthetic id from `fsk_users` has no inherent customer meaning and should be marked as 4Shark-generated. The pre-PR-#2120 logic skipped the prefix in managed mode, on the implicit assumption that "managed" meant "4Shark-controlled", but the synthetic id is the strongest case for the prefix.

PR #2120 collapsed the three modes into the two-mode rule above, on the new `Source#user_id_from` method, and inverted the polarity of the managed branch. Mode 1's responsibility moved to `IdentifierPrefixerTransformer`; mode 2 became the "non-normalized passes through" rule; mode 3's default became the "normalized prepends" rule.

PR #2174 then deleted the `ApplicationConfiguration.managed_integration?` flag entirely (along with `self_service_integration?`, `api_integration?`, `database_integration?`, and `integration_mode`). The flag survived in two unrelated callers (a view template and an initializer); both moved to `Integrator.fully_normalized?`, a top-level helper that answers a different question (see below).

## `Integrator.fully_normalized?` — not the identifier rule

`lib/integrator.rb` exposes a top-level helper:

```ruby
module Integrator
  def self.fully_normalized?
    Source.size == 1 && Source.normalized.size == 1
  end
end
```

This is **not** the identifier rule. It is a configuration shape question: "does this integrator have exactly one Source, and is that Source the normalized one?". The helper is consulted in two places:

- **`integration_report_mailer/create.html.erb`** — the customer-facing email shows different summary content for fully-normalized integrators (database version + integration version) than for hybrid setups (per-source/per-stream stats). The helper picks the branch.
- **(historical)** — a symmetric encryption initializer used to gate keys on `managed_integration?`. PR #2174 made the initializer unconditional in production, so the helper has only one caller now.

The identifier rule cares about the **per-Source `normalized` flag**, not about the integrator's overall shape. A hybrid customer with one normalized Source and one ApiSource gets `'4sk_42'` on records from the normalized one and pass-through on records from the API one — the identifier rule is per-record, decided by which Source the record came from. `Integrator.fully_normalized?` is an integrator-wide property used for reporting concerns; the two helpers operate at different layers and should not be confused.

## Where the rule is invoked

The rule is consulted at two stages of the pipeline:

1. **`request_body_for(import)` on Resource subclasses** — when constructing the JSON body of the API call, every place the body references a User by identifier (the user being registered, the user's parent, the user's manager, the seller of a deal, the recipient of a goal) calls `import.stream.source.user_id_from(import.data[:some_field])`. The prefix is applied at body-construction time.
2. **Loader Consumers** — when the loader needs to resolve a user identifier from a stored Import (e.g., to attach a deal to a previously-registered user), it calls `import.stream.source.user_id_from(...)` to reconstruct the same identifier the platform expects.

In both cases, the call goes through the **Stream**'s Source (`import.stream.source.user_id_from`), not through the Resource model. This matters when a customer has multiple Sources contributing to the same Resource: the Source that produced *this* particular record is the one whose rule applies, not some default.

## What the rule deliberately does not do

- **It does not look up the user.** `user_id_from` is a string transformation, not a query. It cannot fail; it does not raise; it does not need the database.
- **It does not check whether the user exists on the platform.** That's the API's job. If the integrator emits `'4sk_999'` for a user that was never registered, the API rejects the call; the integrator records the rejection in the audit trail and moves on.
- **It does not handle the platform's internal id at all.** The platform-side id translation is a separate mechanism (Deliverable 1, Chapter A); the integrator is unaware of it.
- **It does not vary by Resource.** A Deal referencing a User uses the same rule the User stream itself uses. A Goal scoped to a Group uses the same rule for the user_id lookup. The rule is a Source property, not a Resource property.

## Summary

`Source#user_id_from(id)` returns `'4sk_#{id}'` for normalized Sources and `id` for everything else. Two modes, no flags, no per-Source prefix configuration, no fallbacks. The `'4sk_'` prefix is a marker that the identifier was generated by 4Shark's normalized contract; non-normalized identifiers are the customer's own truth and pass through. The historical three-mode logic was wrong about polarity and overloaded responsibilities; the current shape is what it should have been from the start.
