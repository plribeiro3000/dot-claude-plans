Title: "PermissionRequest hooks not triggered for subagent permission
        requests in Agent Teams"

Verbatim quotes (from the fetch):

Expected behavior:
"PermissionRequest hooks should fire for all permission requests, including
those delegated from subagents to the parent session. The hook should
intercept the request before it reaches the terminal UI, regardless of

Actual behavior (as summarized from the fetch, reflecting the reporter's

underlying mechanism described (a subagent's permission request not
reaching the configured hook, falling back to a terminal prompt in the
parent session instead) is not qualified in the fetched text as exclusive
to the "Teams" feature specifically as opposed to any Task-tool-spawned
subagent — but this spike did not find a source that tests the plain
single-subagent case in isolation from "Agent Teams."

## Fresh external evidence — PreToolUse vs PermissionRequest ordering

--- dyad.sh blog post (fetched via WebFetch, 2026-07-01) ---
URL: https://www.dyad.sh/blog/claude-code-permission-hooks

Verbatim quote:
"If neither of them catches the request, and Claude Code would normally
show a permission dialog, the PermissionRequest hook fires."

Relevance: this is a secondary (blog) source, not primary Anthropic
documentation -- flagged as such. It is consistent with, and sharper than,
the two primary-source excerpts already captured in `approval_doc_1.txt`
and `approval_doc_2.txt` for the source SPIKE.md:
  - approval_doc_1.txt: "A hook that exits with code 2 stops the tool call
    before permission rules are evaluated, so the block applies even when
    an allow rule would otherwise let the call proceed."
  - approval_doc_2.txt: PermissionRequest fires "When a permission dialog
    appears."
Read together: a PreToolUse `exit 2` stops the call before permission
rules are evaluated -- i.e., before the point where Claude Code would
decide a dialog is needed -- so for a call a PreToolUse hook blocks, the
"permission dialog would appear" condition that triggers PermissionRequest
is never reached. The dyad.sh quote states this outcome directly ("if
neither of them catches the request... PermissionRequest fires"), which
this spike treats as corroborating, not sole, evidence -- no single
primary-source Anthropic document was found stating the PreToolUse-vs-
PermissionRequest precedence in one place.

## What this auxiliary file supports (used in PLAN-SPIKE.md's Implementation
   Option — A/B ordering & interaction section)

1. The best-supported reading, combining the primary-source excerpts
   (`approval_doc_1.txt`, `approval_doc_2.txt`) with the fresh dyad.sh quote,
   is that a PreToolUse `exit 2` block pre-empts PermissionRequest entirely
   for the SAME call in the main session — PermissionRequest never reaches
   its firing condition once PreToolUse has already blocked.
2. For subagent-originated Bash calls specifically, the fresh evidence
   (issue #23983 for PermissionRequest, issue #34692 for PreToolUse/
   PostToolUse generally) points toward NEITHER hook type reliably
   intercepting a subagent's Bash call — though #34692 and the UNVERIFIED
   #40580/#26923 disagree on the exact mechanism (hook does not fire at all,
   vs. hook fires but exit code is ignored). Either way, the practical
   consequence for 4Shark's option space is the same: implementing B
   (PermissionRequest) is not evidenced to close a subagent gap that A
   (PreToolUse, i.e. extending `validate-bash-command.sh`) leaves open.
3. Neither of these two findings was independently re-derived from a
   4Shark-owned empirical test (e.g., actually spawning a subagent in this
   session and observing whether a matching PermissionRequest hook fires)
   — that remains a test-to-run recommendation, not a closed question, per
   the source SPIKE.md's own "What remains uncertain" framing extended to
   this narrower point.
