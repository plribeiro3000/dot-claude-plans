1. Base image

Pritunl (the VPN server) has no official Docker image — Docker Hub's pritunl org publishes only pritunl-zero and pritunl-bastion, a different product. Every candidate is a community image.

A. jippi/docker-pritunl

Published to ghcr.io, Docker Hub, and AWS public ECR

Pros

  • +Three registries, including AWS public ECR (no third-party pull-through needed)
  • +Explicit external-Mongo env var (PRITUNL_MONGODB_URI)
  • +Documents both --network=host and explicit-port alternatives
  • +Has a version-tagged release history (Renovate can track FROM)

Cons

  • −Unofficial — supply chain trust rests on one external maintainer
  • −privileged: true shown in every example (see Runtime sub-decision)

2. Runtime / launch type

Grounded fact: Pritunl in a container needs privileged: true or /dev/net/tun passthrough, host-loaded WireGuard kernel modules, and host or explicit-port networking. Fargate does not expose host kernel modules or privileged mode — it is out.

A. ECS on EC2, dedicated container instance — CHOSEN

One EC2 host running the ECS agent, one task, privileged + host networking

Pros

  • +4Shark already runs ECS-EC2 elsewhere (app-outbound, integrators, onboarding, setup all use modules/ecs_service + modules/ecs_capacity) — a known operational pattern
  • +Preserves the WireGuard-kernel-module and host-networking requirements the current VM already satisfies

Cons

  • −modules/ecs_service hardcodes network_mode = bridge for EC2 and has no privileged flag — new Terraform work needed (extend the module or write bespoke resources, as modules/pritunl already does today)
  • −Single container instance = single point of failure unless a second stands by (ASG min/max=1 is the current VM's posture too, so this is not a regression, just not an improvement)
terraform/modules/ecs_service/main.tf:14 — network_mode = var.launch_type == "FARGATE" ? "awsvpc" : "bridge" (no privileged/host branch); terraform/modules/ecs_capacity/main.tf:53-102 (ASG-backed EC2 capacity provider pattern already in the fleet)
New Terraform: ModerateFargate-compatible: No

B. ECS on EC2 + NLB with UDP listeners — NOT chosen

Same EC2/privileged container, fronted by a Network Load Balancer

Pros

  • +NLB supports a static Elastic IP per AZ, so the fixed-IP constraint (see Networking sub-decision) can still be met
  • +Opens a path to multi-instance HA later without re-architecting the entry point

Cons

  • −NLB does not solve MongoDB/session-state sharing across instances — HA still needs a plan for Pritunl's own state, which is not stateless
  • −More infrastructure than the current single-VM topology for a VPN gateway whose load profile has not required HA to date
  • −Adds an NLB cost + operational surface not present today
terraform/vpn/README.md:5-6 — current topology is a single t3a.micro; no HA requirement documented today
New Terraform: HighFargate-compatible: No

C. Fargate (ruled out by grounded facts)

Listed for completeness — not viable

Pros

  • +Would match the pgbouncer/connection-pooler and keycloak precedent (both Fargate)

Cons

  • −Fargate does not support privileged: true, host-loaded kernel modules, or network_mode: host — all required by every community Pritunl image
terraform/app-shared-001/connection_pooler.tf + modules/connection_pooler/main.tf:250-260 — the two existing tool-repo precedents (connection-pooler, auth-001) both run requires_compatibilities = ["FARGATE"], confirming no existing 4Shark tool repo has solved the privileged/host-network case on Fargate
New Terraform: N/AFargate-compatible: N/A (ruled out)

3. MongoDB

Pritunl's current org/users/VPN profiles live in the running VM's local MongoDB (see terraform/modules/pritunl/README.md:111 — "OpenVPN routes ... and client profiles are configured inside Pritunl directly"). Whatever is chosen must carry this state across the cutover.

A. Amazon DocumentDB

Managed MongoDB-compatible service

Pros

  • +Fully managed — no MongoDB patching/backup ops

Cons

  • −Explicitly unsupported by Pritunl: "Pritunl, Pritunl Zero and Pritunl Cloud all utilize capped collections and tailable cursors for publish subscribe messaging. This prevents using the MongoDB API compatible databases such as DocumentDB." — a hard blocker, not a tuning issue
forum.pritunl.com/t/is-aws-documentdb-supported-as-a-database/1299 — verbatim quote above, confirmed current (no fix timeline given)
Viability: BlockedMigration effort: N/A

B. MongoDB container/sidecar with persistent EBS — CHOSEN

Self-managed Mongo, same task or same instance, EBS-backed volume

Pros

  • +Closest architectural match to today (Mongo colocated with Pritunl)
  • +Supports capped collections/tailable cursors — no Pritunl compatibility issue
  • +A straightforward mongodump/mongorestore migrates the existing state

Cons

  • −ECS-EC2 bridge-mode volume persistence needs an EBS-backed host path (or a separate EBS-backed volume mount) tied to the specific container instance — instance replacement needs care so the volume reattaches
  • −4Shark still owns MongoDB version upgrades/patching, same as today
ansible/roles/4shark.pritunl/tasks/main.yml:56-61 — current MongoDB 8.0 self-managed via apt; terraform/modules/ecs_service/main.tf:56-62 — the module already supports a volume block with host_path
Migration effort: LowOps burden: Same as today

C. Small dedicated MongoDB VM (kept outside the container) — NOT chosen

Decouple Mongo's lifecycle from the Pritunl container entirely

Pros

  • +Mongo state survives a Pritunl container/task replacement independently — no volume-reattachment coordination
  • +Matches the jippi/goofball222 "external MongoDB" model directly (PRITUNL_MONGODB_URI / MONGODB_URI)

Cons

  • −Keeps one VM in the topology — only Pritunl itself is containerized, not the full stack
  • −Adds a network hop + a security-group rule between the ECS instance and the Mongo VM
github.com/jippi/docker-pritunl README: "If you have MongoDB running somewhere else you'd like to use, you can do so through the PRITUNL_MONGODB_URI env var"
Migration effort: LowestOps burden: Same as today, isolated

4. Networking / public entry

Existing .ovpn profiles and WireGuard client configs are pinned to the current Elastic IP. Repointing every engineer's client config is a coordination cost the option comparison below must account for.

A. EIP directly on the ECS container instance's ENI — CHOSEN

Same EIP-association model as today, just re-pointed at the new instance

Pros

  • +The EIP allocation itself can be reused — only the aws_eip_association target changes, so the public IP address does not have to change
  • +Zero client reconfiguration if the same EIP is reassociated
  • +Simplest possible mapping from the current architecture

Cons

  • −Single instance = single point of failure for the public entry point (same as today)
terraform/modules/pritunl/main.tf:32-44 — aws_eip + aws_eip_association against the instance today; the EIP allocation is a distinct resource from the instance and survives instance replacement if re-associated
Client reconfig: NoneEffort: Low

B. NLB with UDP listeners + EIP on the NLB — NOT chosen

Front the container with a Network Load Balancer

Pros

  • +NLB supports a static EIP per AZ — a fixed public IP is still achievable
  • +Decouples the public IP from any single container instance's lifecycle

Cons

  • −If the NLB's EIP differs from today's, every engineer's .ovpn/WireGuard config needs updating — a coordinated cutover event
  • −More infrastructure (target group, health checks, UDP listener behavior) for a gateway that has run on a bare EIP association without issue
Same runtime sub-decision Option B citation applies — NLB is the same infra either way
Client reconfig: Possible (unless EIP is migrated to the NLB)Effort: Higher

A. Main-only (pgbouncer reference) — CHOSEN

Single protected main, merge-to-main == ships

Pros

Cons

  • −No pre-production validation step for a new Pritunl base-image version before it reaches the one gateway every engineer depends on

7. Cutover

Per DEPLOYMENT-STRATEGY.md's decision framework: phase only if the in-flight contract breaks backward-incompatibly. A VPN gateway has no Computation-tracked background jobs, but it does have long-lived client connections and irreplaceable state (org/users/profiles) — the framework's other triggers (irreversible data-shape change, cross-service contract) are what apply here, not the Sidekiq-specific ones.

A. Maintenance window — drain, migrate, cut over — CHOSEN (with a pre-flip parallel validation step)

Dump/restore Mongo state, stop the old instance, start the new one, reassociate the EIP, during a scheduled low-traffic window

Pros

  • +Simplest to reason about — one clean state transfer, no dual-write complexity for VPN org/user data
  • +Matches DEPLOYMENT-STRATEGY.md's "drained maintenance window" single-deploy condition

Cons

  • −Every connected engineer is disconnected during the window and must reconnect
  • −Requires coordinating a window across the team (VPN is how engineers reach private infra, including for their own work)
~/.claude/docs/DEPLOYMENT-STRATEGY.md — "a maintenance window (weekend / dawn) with the queue drained" — the maintenance-window condition generalizes to VPN sessions drained rather than Sidekiq queue drained
Downtime: Short, scheduledRollback: Keep old VM stopped, not destroyed, until validated

B. Parallel run — new gateway on a new IP, migrate clients gradually, then retire the old one — NOT chosen

Stand up the ECS-based Pritunl alongside the existing VM, reissue client profiles progressively

Pros

  • +No hard cutover moment — engineers migrate on their own schedule
  • +New instance fully validated with real traffic before the old one is retired

Cons

  • −Org/user state exists in two places during the transition — new users created against which instance? Needs an explicit single-source-of-truth rule for the parallel period
  • −If the fixed-EIP constraint (sub-decision 4) holds, a parallel run needs a second, temporary public IP — every client gets a temporary profile, then a second reconfiguration back to the final IP if the EIP is reused at the end
  • −Longest wall-clock exposure — two gateways to secure and patch simultaneously
terraform/modules/pritunl/README.md:111 — "OpenVPN routes ... and client profiles are configured inside Pritunl directly" confirms state lives only in Pritunl's own Mongo, so a parallel run genuinely forks that state unless one instance is designated authoritative
Downtime: NoneRollback: Trivial (old VM still live)
