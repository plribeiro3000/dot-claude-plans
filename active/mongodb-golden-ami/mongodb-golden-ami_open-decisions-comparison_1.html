Decision 1 — Where does the Packer template + build CI live?

The `ansible` repo already owns `4shark.mongodb8` and is already HubFlow-governed with the min-age gate, but has no build-on-merge CI today. The Docker-tool-repo standard (pgbouncer/keycloak shape) is explicitly container-scoped, not AMI-scoped.

Option A — inside the `ansible` repo

Co-located with the role it bakes.

Pros

  • +One PR changes role and image together
  • +HubFlow + min-age gate already wired
  • +Reuses the existing `packer/` directory name

Cons

  • −Still net-new CI work — no build-on-merge exists today
  • −Mixes "provisioning source" with "artifact producer"
  • −Every `ansible` CI run potentially waits on an AMI build
Cost: LowerRisk: Repo coupling
Engineer's choice

Option B — new dedicated repo

Mirrors the pritunl/keycloak tool-repo shape, adapted for an AMI deliverable.

Pros

  • +Clean separation of provisioning source vs artifact
  • +Independent CI cadence from `ansible`'s own commits

Cons

  • −Stretches a container-oriented standard onto an AMI
  • −Needs cross-repo role checkout/dependency
  • −Another repo to govern, another renovate.json, another min-age wiring
Cost: HigherRisk: Cross-repo coordination
Engineer's choice

Decision 2 — AMI reference mechanism in Terraform

Every integrator stack currently hardcodes the AMI id with `ignore_changes = [ami, ...]`. Adopting a versioned pipeline means deciding how Terraform learns which AMI is current.

Option A — `data "aws_ami"` most_recent + filter

Terraform reads the latest matching AMI at plan time.

Pros

  • +No extra AWS resource or state to manage
  • +Matches HashiCorp's own documented pattern

Cons

  • −Implicitly mutable — every plan can pick up a newer AMI
  • −Cuts against reproducible/auditable plans unless pinned per environment
Cost: LowerRisk: Unintended rollout
Engineer's choice

Option B — SSM Parameter Store pointer

Pipeline writes the AMI id; Terraform reads it — same pattern already used for subnet ids in these stacks.

Pros

  • +Explicit, versioned promotion pointer
  • +Already-idiomatic pattern in this codebase (`data "aws_ssm_parameter"`)

Cons

  • −New pipeline IAM permission needed
  • −Needs an explicit write-trigger decision (ties to Decision 3)
  • −Silent staleness if the parameter update is forgotten
Cost: MediumRisk: Forgotten promotion step
Engineer's choice

Option C — Terraform var bumped per PR

Closest to today's shape, just versioned instead of eternal.

Pros

  • +Zero new AWS resource or IAM permission
  • +Every change is a reviewable, auditable PR diff

Cons

  • −Fully manual promotion, per stack, per rebuild
  • −Does not reduce the toil the initiative is partly meant to remove
Cost: Lowest engineeringRisk: Highest ongoing toil
Engineer's choice

Decision 3 — AMI versioning + promotion trigger

Renovate's `aws-machine-image` datasource is explicitly marked experimental by Renovate's own docs — a different risk posture than the mechanically-verified datasources 4Shark relies on elsewhere.

Option A — automated cadence

Scheduled rebuild, auto-proposes the new AMI (e.g. via Renovate).

Pros

  • +Patches flow in without a human remembering to trigger a build
  • +Can mirror the `docker`/`deb` datasource pattern already in use

Cons

  • −`aws-machine-image` datasource is experimental (Renovate's own docs)
  • −No 7-day-quarantine-style gate exists for AMIs today
  • −Useless without a consumer that promotes it (ties to Decision 2)
Cost: Higher upfrontRisk: Unvetted DB patch auto-ships
Engineer's choice

Option B — manual/on-demand build

`workflow_dispatch` or triggered by a role change; explicit promotion.

Pros

  • +Mirrors the build/deploy split 4Shark already trusts for tool repos
  • +No dependency on an experimental datasource

Cons

  • −Relies on someone noticing an upstream patch
  • −Shifts manual toil rather than removing it
Cost: Lower upfrontRisk: Silent staleness
Engineer's choice

Decision 4 — Integrator production cutover sequencing/automation (Phase 3)

Touches 15 production Mongo VMs across 5 client replica sets — the highest-risk decision in this plan.

Option A — Terraform `-replace` + rolling, orchestrated

Scripted, repeatable, reused across all 5 stacks.

Pros

  • +Consistent, repeatable, less manual keystroke risk

Cons

  • −Terraform has no native awareness of MongoDB's rolling-upgrade discipline
  • −Needs an external wrapper/orchestration layer around `terraform apply`
Cost: Higher upfrontRisk: Less human judgment per step
Engineer's choice

Option B — manual runbook-driven

Secondaries first, wait for SECONDARY, step-down + replace primary last.

Pros

  • +Directly follows documented MongoDB rolling-upgrade practice
  • +Matches 4Shark's existing `/runbook` pattern
  • +Maximal human judgment for a first-of-its-kind production change

Cons

  • −15 replacements done by hand the first time through
  • −No automatic guardrail beyond the runbook's own discipline
Cost: Lower engineeringRisk: Human sequencing error
Engineer's choice

Decision 5 — Pritunl Mongo VM topology (Phase 2)

The greenfield Pritunl Mongo VM's own availability requirement has not been researched by any prior spike — flagged as an open question, not assumed.

Option A — single-node

One `mongod`, no replica set.

Pros

  • +Matches "VPN doesn't need integrator-grade HA" reasoning
  • +Simpler AMI consumer — no `rs.initiate()`, no arbiter sizing
  • +Keeps the first pipeline adopter genuinely low-risk

Cons

  • −No automatic failover — single point of failure
  • −Diverges from the integrator fleet's PSA precedent
Cost: LowerRisk: SPOF; availability need not researched
Engineer's choice

Option B — PSA (mirrors integrator topology)

Primary + secondary + arbiter across 2 AZs.

Pros

  • +No second post-boot config shape to build/test
  • +Automatic failover, consistent with integrator HA reasoning
  • +Better dress rehearsal for Phase 3's larger rollout

Cons

  • −3× the VM/EBS footprint of Option A
  • −Reintroduces complexity the VM-not-container decision tried to avoid
Cost: HigherRisk: Bigger debug surface for a first adopter
Engineer's choice
