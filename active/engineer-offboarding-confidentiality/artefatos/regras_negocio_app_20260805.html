Regras de negócio do app — inventário de ativos

Varredura completa do repositório principal · 5 de agosto de 2026 · 12 famílias, 47 regras identificadas · cada uma com a evidência em código e um campo para você corrigir

O que essa varredura procurou

Depois da sua calibragem, mudei a lente. Não procurei "código bom" nem "arquitetura" — procurei invariantes de negócio: regras da forma "X não pode ser alterado depois que Y", "só pode Z se W", "cancela mas não apaga", "clona para contornar". Cada uma dessas é uma decisão comercial que alguém tomou depois de um problema real.

O achado central: o padrão que você descreveu não é um caso isolado do incentivo — é uma família aplicada a seis entidades diferentes, de forma consistente. Isso é muito mais forte juridicamente do que uma regra solta, porque demonstra desenho deliberado e não coincidência.

FAMÍLIA 1Reutilização, imutabilidade e clone

Esta é a família que você descreveu, e ela é maior do que o incentivo. A regra completa é: um objeto de configuração pode ser reutilizado por vários consumidores; no instante em que ganha o primeiro consumidor, torna-se imutável; e o clone existe para permitir a variação sem quebrar a imutabilidade. Está aplicada a seis entidades.

F1.1Incentivo amarrado a plano não pode ser alteradoAtivo forte

A regra em português
Um incentivo pode ser usado por vários planos. Assim que o primeiro plano o usa, ele congela — nem o dono nem um administrador consegue editá-lo, e isso independe de o plano estar ativo, cancelado ou desativado.

# app/app/policies/incentive_policy.rb:12-19
def update?
  return false if user.company_id != record.company_id
  return false if record.disabled?
  return false if record.plans.any?
  return true if role.permission?('incentive_update')

  record.owner_id == user.id && user.permission?('incentive_update')
end

Por que é ativo
A alternativa óbvia — versionar o incentivo, ou permitir editar e recalcular — é o que um sistema novo faria. Vocês escolheram congelar, porque uma comissão já paga precisa continuar explicável com a regra que a gerou. Essa é uma decisão de produto financeiro, não de engenharia.

F1.2O clone é a válvula de escape — e a assimetria é deliberadaAtivo forte

A regra em português
Como o incentivo congelado não pode mudar, o cliente clona, ajusta o detalhe que precisa e usa o clone no plano novo. O clone é permitido mesmo em incentivo já amarrado a plano.

# app/app/policies/incentive_policy.rb:28-34
def clone?
  return false if user.company_id != record.company_id
  return false if record.disabled?
  # ← note: NÃO existe `return false if record.plans.any?` aqui
  return true if role.permission?('incentive_clone')

  record.owner_id == user.id && user.permission?('incentive_clone')
end

Por que é ativo, e por que é difícil de negar
A regra não está escrita em lugar nenhum como frase — ela existe como a diferença entre dois métodos vizinhos: um guard presente no update? e ausente no clone?. E o clone tem permissão própria (incentive_clone), separada de criação e de edição — ou seja, o cliente pode dar a alguém o direito de clonar sem dar o de criar do zero. Reproduzir essa combinação por acaso é implausível.

F1.3A mesma regra, um nível acima: rankificador usado por incentivo congelaAtivo forte

A regra em português

F2.2Cancelado é estado terminal — e só se cancela um plano aprovado sem nenhuma declaração aceitaAtivo forte

A regra em português
Isso é exatamente o que você descreveu. O plano só pode ser cancelado se estiver aprovado (final), ativo, e nenhuma declaração tiver sido aceita por ninguém. Uma vez cancelado, não há volta: nenhuma transição sai de canceled.

# app/app/models/plan.rb:117-144 — a máquina de estados
state_machine :status, initial: :initial do
  event :finish_registration { transition initial: :processing }
  event :finish_processing   { transition processing: :review,  if: manager_legal_module?
                               transition processing: :final,   unless: manager_legal_module? }
  event :approve             { transition review: :approving }
  event :finish_approving    { transition approving: :final }
  event :rollback            { transition review: :initial }
  event :cancel              { transition final: :canceled }
  # não existe nenhuma transição PARTINDO de :canceled
end

# app/app/policies/plan_policy.rb:56-64
def cancel?
  return false unless record.final?
  return false unless record.enabled?
  return false if record.statements.with_status(:accepted).any?

Por que é ativo
A regra "não pode cancelar se alguém já aceitou a declaração" é pura decisão de negócio: uma vez que o participante aceitou o extrato dele, a empresa perdeu o direito de desfazer o plano. Isso é uma proteção do participante embutida no produto, e nenhum técnico deduz que ela deveria existir.

F2.4O caminho de aprovação depende de um módulo do clienteAtivo forte

FAMÍLIA 3O calendário como unidade de tempo separada

Você citou a separação calendário↔plano como ativo. Ela é maior do que uma separação de tabelas — o calendário carrega um conjunto de regras de fechamento que codifica como o ciclo de comissão se encaixa no ciclo de folha do cliente.

F3.1O dia de fechamento tem de bater com a data de inícioAtivo forte

A regra em português
Um calendário mensal que começa dia 16 tem de fechar dia 15. Um semanal que começa na segunda tem de fechar no domingo. E há um atalho: se começa dia 1 e fecha no último dia do mês, é sempre válido. Clientes no modo easy não passam por essa validação.

# app/app/models/calendar.rb:110-120
def correct_closing_day
  return if starts_at.blank? || closing_day.blank? || ends_at.blank?
  return if company.easy?
  return if starts_at.day == 1 && closing_day.to_i == ends_at.end_of_month.day

  if weekly? || biweekly?
    errors.add(:closing_day, :invalid) unless starts_at.wday == (WeekDayCalculator.call(closing_day) + 1) % 7
  else
    errors.add(:closing_day, :invalid) unless (starts_at - 1.day).day == closing_day.to_i
  end
end

Por que é ativo
Essa aritmética — (starts_at - 1.day).day == closing_day, e o deslocamento +1 % 7 para semanas — é a codificação de como um ciclo de apuração se alinha ao fechamento de folha no Brasil e na América Latina. Não está em manual nenhum. E a carve-out do dia 1 existe porque o caso mais comum precisava passar sem depender do cálculo.

F3.2Nem todo calendário aceita métricasAtivo forte

A regra em português
Calendário semanal sempre aceita métrica. Mensal só aceita se cobrir o mês inteiro (começa dia 1 e termina no último dia). Qualquer outra frequência não aceita.

  return false unless monthly?

E a regra que a consome, no plano
O plano só é válido se toda métrica com intervalo estiver contida em algum período do calendário dele:

Por que é ativo

A mensagem de erro que o cliente vê é "Combinação de métricas das incentivações é inválida" — e por trás dela existe um casamento de três objetos (calendário, período, métrica) com regras de compatibilidade que só fazem sentido depois de anos vendo clientes montarem ciclos incompatíveis.

F3.3Períodos e intervalos são derivados, e regerados quando o calendário mudaAtivo médio

A regra em português
Ao criar um calendário, o sistema gera automaticamente seus períodos e intervalos conforme a frequência — geradores diferentes para semanal/quinzenal, avulso e mensal. Se o calendário for editado, tudo é apagado e regerado; mas se a mudança foi só ativar/desativar, não regera.

# app/app/models/calendar.rb:122-153

  elsif single?               then periods.create(starts_at:, ends_at:, number: 1)
  else                             MonthlyPeriodsGenerator.call(calendar: self)
  end
end

  return if saved_change_to_attribute?(:disabled_at)   # desativar não regera
  periods.destroy_all
  create_periods
end

Ressalva
Médio: a geração em si é mecânica. O ativo é a guarda do disabled_at — sem ela, desativar um calendário destruiria e recriaria todos os períodos, invalidando comissões históricas. Alguém descobriu isso do jeito difícil.

F3.4O calendário fecha a janela de aceite da declaraçãoAtivo forte

A regra em português
O participante só pode aceitar a declaração dele enquanto o calendário não terminou. Passou a data final, a janela fecha — e fecha também se o plano foi cancelado ou desativado.

FAMÍLIA 4O aceite do plano

F4.1Cinco pré-condições simultâneas para aceitar um planoAtivo forte

A regra em português
Para o gestor aceitar um plano, cinco coisas precisam ser verdade ao mesmo tempo: o plano não pode estar desativado; o plano já tem de ter terminado (não pode estar rodando); tem de existir ao menos uma declaração pendente; a comissão tem de estar em revisão ou travada; e a empresa tem de ter o módulo jurídico-operador.

def plan_status
  errors.add(:plan_id, :disabled) if plan.disabled?
end

def plan_time_window
  errors.add(:plan_id, :running) if plan.running?       # só aceita plano encerrado
end

def pending_plan_statements_presence
  errors.add(:plan_id, :statements_pending) if plan.statements.with_status(:pending).blank?
end

def commission_status
  return if commission.review? || commission.locked?

FAMÍLIA 5Hierarquia e quem pode ser responsável

F5.1O gestor tem de estar estritamente acima — e níveis podem ser puladosAtivo forte

A regra em português
Um cargo só pode se reportar a um cargo estritamente mais alto, e pode pular níveis. A regra está codificada como comparação de posição num array ordenado de 11 níveis.

# app/app/models/seat.rb:6-8, 33-39
TYPES = %w[SuperAdmin Admin President VicePresident Director Superintendent
           GeneralManager Manager Coordinator Supervisor SalesRepresentative].freeze

def correct_parent
  return if parent.blank?
  return unless TYPES.find_index(type)
  return if TYPES[0, TYPES.find_index(type)].include?(parent.type)
  errors.add(:parent_id, :invalid)
end

Por que é ativo
A expressão TYPES[0, índice_do_meu_tipo] — "todos os tipos que vêm antes do meu" — é a regra "estritamente acima, pulando níveis" escrita em uma linha. Organizações reais têm ramos rasos e ramos profundos; forçar todos os níveis a existirem tornaria o modelo uma ficção. Essa foi uma escolha.

F5.2Vendedor não pode ser responsável por planoAtivo forte

A regra em português
Existem 11 níveis de cargo, mas só 9 podem ser responsáveis por um plano — SuperAdmin e SalesRepresentative ficam de fora. E o número mínimo de responsáveis muda: dois no geral, um só se a empresa está no modo easy.

# app/app/models/plan.rb:4 e 403-417
RESPONSIBLE_TYPES = %w[Admin President VicePresident Director Superintendent
                       GeneralManager Manager Coordinator Supervisor].freeze
# ← SuperAdmin e SalesRepresentative ausentes, deliberadamente

def responsibility
  return unless company.manager_legal_module?
  return unless responsible_ids_changed? || new_record?

  if company.easy?
    errors.add(:responsible_ids, :size) if responsible_ids.count < 1
  elsif responsible_ids.count < 2
    errors.add(:responsible_ids, :size)
  end

  errors.add(:responsible_ids, :invalid) unless unique_responsible_types.included_in?(RESPONSIBLE_TYPES)
end

Por que é ativo
A exigência de dois responsáveis é segregação de funções: ninguém aprova um plano de comissão sozinho. O vendedor excluído é conflito de interesse — quem recebe não homologa. São regras de governança financeira, não de software, e a mensagem que o cliente vê já está em português: "Plano não tem o número mínimo de responsáveis".

FAMÍLIA 6Participação por histórico, não por estado atual

F6.1Quem participa do plano é quem esteve no grupo durante a janela — não quem está hojeAtivo forte

A regra em português
Para saber quem entra no cálculo, o sistema não olha quem está no grupo agora. Ele consulta o histórico de entradas e saídas e pega todo mundo cuja permanência teve qualquer sobreposição com a janela do calendário.

# app/app/models/plan.rb:173-190
def user_ids(starts_at: nil, ends_at: nil)
  starts_at ||= calendar.starts_at
  ends_at   ||= calendar.ends_at

  groupification_history_range_condition =
    'groupification_histories.starts_at <= ? AND (? <= groupification_histories.ends_at
      OR groupification_histories.ends_at IS NULL)'

  groupification_ids =
    groupification_histories
      .where(groupification_history_range_condition, ends_at, starts_at)
      .pluck(:groupification_id).uniq

  Groupification.where(id: groupification_ids).pluck(:user_id)
end

Por que é ativo
Note a inversão dos argumentos (ends_at, starts_at): é o teste clássico de sobreposição de intervalos, e ele garante que quem entrou no meio do período ou saiu no meio entra no cálculo mesmo assim, para ser rateado. A alternativa óbvia — olhar quem está no grupo hoje — produziria comissão errada para todo mundo que se movimentou. Essa é uma regra que só se descobre quando um cliente reclama do pagamento de alguém que mudou de célula.

Confere? ☐ sim ☐ corrigir: ______________

F6.2Metas por participação puxam a equipe do gestor pelo histórico de hierarquiaAtivo forte

A regra em português
Quando o plano está no modo "metas por participação" (override), além dos participantes diretos ele traz também os subordinados de cada um — e de novo pelo histórico de hierarquia na janela, não pela hierarquia atual. Fora desse modo, a lista de subordinados é vazia.

# app/app/models/plan.rb:199-212
def subordinate_ids(starts_at: nil, ends_at: nil)
  return [] unless override?

  parent_seat_ids = Seat.where(user_id: user_ids).pluck(:id)

  SeatHistory
    .joins(:seat)
    .where('seat_histories.parent_id': parent_seat_ids)
    .where('starts_at < ? AND (? < ends_at or ends_at is null)', ends_at, starts_at)
    .pluck(:user_id)
end

E a regra que proíbe a combinação
Um plano não pode ser ao mesmo tempo "metas compartilhadas" e "metas por participação" — os dois conceitos se excluem:

# app/app/models/plan.rb:385-390
def shared_conditions
  return unless shared? && override?
  errors.add(:shared, :invalid)
  errors.add(:override, :invalid)
end

FAMÍLIA 7O motor de fórmulas e sua taxonomia de erros

F7.1Doze erros de fórmula, cada um com mensagem própria em linguagem de negócioAtivo forte

A regra em português
O sistema reprova uma fórmula antes de salvar, com doze diagnósticos distintos. Não é "fórmula inválida" — é "usa a variável X, que não existe", "usa a variável de texto Y em uma conta", "chama a função Z sem argumentos".

# app/config/locales/pt-BR/models/rule.yml:12-24
value:
  division_by_zero:               'divide por zero'
  invalid_date:                   'usa uma data inválida: %{excerpt}'
  node_invalid:                   'tem uma estrutura incompleta'
  parse_error:                    'tem um trecho não reconhecido: %{excerpt}'
  too_few_operands:               'tem uma operação com valores faltando (esperados %{expected}, encontrados %{actual})'
  too_many_closing_parentheses:   'tem um parêntese fechado a mais'
  too_many_opening_parentheses:   'tem um parêntese que não foi fechado'
  too_many_operands:              'tem uma operação com valores em excesso'
  text_in_arithmetic:             'usa a variável de texto %{variable} em uma conta'
  too_few_arguments:              'chama a função %{function} sem argumentos'
  undefined_function:             'usa a função %{function}, que não existe'
  unknown_variable:               'usa a variável %{variable}, que não existe'

F7.2Regra que não calcula rende zero — não interrompe a comissãoAtivo forte

A regra em português

A conclusão que mudou com esta varredura

Antes eu descrevia os ativos como itens soltos — uma lista, um mecanismo, um catálogo. Depois de varrer com a sua lente, o quadro é outro: existe um princípio de desenho aplicado consistentemente ao produto inteiro, que é "configuração é reutilizável até ser usada; a partir daí é imutável, e a variação se faz por cópia". Ele aparece em seis entidades de configuração (Família 1), no plano (Família 2), no artefato entregue (F11.2) e no usuário anonimizado (F10.2).

Isso importa juridicamente por uma razão específica: uma regra isolada pode ser coincidência, mas um princípio aplicado em nove lugares diferentes, do mesmo jeito, não é. Se um produto de terceiro reproduzir esse desenho, a convergência é evidência muito mais forte do que qualquer trecho de código copiado.

Todas as 47 regras foram lidas diretamente no código, com arquivo e linha. Nenhuma foi inferida a partir de nome de método ou de documentação. Marque o que estiver errado, acrescente o que faltou — e me diga especialmente onde eu classifiquei como "médio" algo que você sabe que é forte, porque nesses casos falta contexto de negócio que só você tem.
