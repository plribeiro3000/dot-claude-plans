Requisito não atendido 1 · O índice único está no grão errado — num id sequencial, não na chave de negócio
tb_dim_indicadores_score — o único índice do banco.

Pedimos um índice único no grão período + pessoa + programa + indicador. O que existe é um PK clustered numa coluna só, NR_CHAVE_EMPRESA_MES_RE, que é um número sequencial (id técnico), não a chave de negócio. Ele garante que o contador não repete — trivial — mas não impede duas linhas do mesmo período/pessoa/programa/indicador. O grão real de negócio (DT_DATA, NR_RE, NR_SERVIVIO_CODIGO, NR_ID) hoje é único no dado (3.995 combinações = 3.995 linhas), mas não tem índice nenhum. Se a carga rodar duas vezes, duplica e o banco aceita.

-- Chave é sequencial, faixa gigante para poucas linhas:
chave_min = 1.008.527   chave_max = 3.061.325   linhas = 3.995
-- Grão de negócio já é único, mas sem índice:
grao (DT_DATA+NR_RE+NR_SERVIVIO_CODIGO+NR_ID) = 3.995  = total_linhas
grao sem indicador                            =   435  (uma pessoa tem varios indicadores/mes)
Pedir: índice único composto em (DT_DATA, NR_RE, NR_SERVIVIO_CODIGO, NR_ID). O id sequencial não serve como garantia de unicidade de negócio.
Requisito não atendido 2 · A coluna llave não foi criada no catálogo
tb_dim_indicadores — o catálogo de indicadores.

O pedido nº 1 do catálogo era uma coluna de texto llave, not null e única, com a chave da Variable 4Shark de cada indicador. O catálogo continua com as mesmas 17 colunas de antes — a coluna não existe. Sem ela, a cadeia de resolução da nossa integração (score.NR_ID → catálogo → llave → Variable) não fecha.

Pedir: criar llave no catálogo, texto, not null, único, e a Atento carregar uma chave por indicador a partir daí.
Quebra a integração 3 · 32 linhas de score apontam para indicador que não existe no catálogo
Join score.NR_ID → catálogo.NR_ID — o join que a nossa integração faz em toda carga.

De 220 indicadores distintos no score, 212 existem no catálogo e 8 não existem — 32 linhas órfãs. Na nossa integração cada linha órfã é uma linha rejeitada. Integridade referencial score→catálogo quebrada.

nr_id_distintos_score = 220
nr_id_no_catalogo     = 212   -- 8 indicadores sem catalogo
linhas_sem_catalogo   =  32   -- linhas de score orfas
Pedir: garantir que todo indicador do score exista no catálogo (os 8 faltantes). Ressalva: NR_ID é float no score e int no catálogo — parte pode ser artefato de conversão; validar os 8 caso a caso.
Quebra a integração 4 · A chave do indicador (NR_ID) é float
tb_dim_indicadores_score — a coluna que resolve o indicador.

O indicador agora vive em NR_ID, tipada como float. Uma chave de join em ponto flutuante é frágil: o join com o catálogo (int) depende de conversão implícita e é sujeito a imprecisão. Chave de identidade deveria ser inteira.

Pedir: tipar NR_ID como inteiro no score, coerente com o catálogo.
Requisito não atendido 5 · Datas de criação/atualização como date e com nomes da proposta deles
tb_dim_indicadores_score — colunas de auditoria da linha.

As colunas entraram como DT_CREATED / DT_MODIFIED (os nomes da proposta da Atento), não os do nosso script (DT_CREACION / DT_ACTUALIZACION), e tipadas como date — só o dia, sem hora. A leitura incremental (ler só o que mudou desde a última carga) depende de um carimbo com hora; com date, duas mudanças no mesmo dia ficam indistinguíveis. Sinal claro de que aplicaram o arquivo deles, não o nosso script de 20-ago.

Pedir: tipar as datas como datetime (com hora), e alinhar o nome com o nosso script para a leitura incremental funcionar.
