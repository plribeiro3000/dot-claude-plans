# Plan: Atento México — Informe Corporativo de Utilización

## Overview

**Topic:** atento-mexico-informe-corporativo
**Type:** Single-client content deliverable (PPT + supporting XLSX)
**Status:** 🟢 Delivered (v10, Jul/2025–May/2026, sent 2026-06-18) — new requirement: convert into a recurring/periodic deliverable (see Follow-up)

## Context

Atento México is a politically sensitive account. The client has been signaling — through repeated delays, friction on every request, and noise at multiple levels — that they may want to cancel the contract. There is also internal suspicion of fraud on their side.

The global Atento team has asked for evidence that the platform is being used by end users at the México operation. The most direct platform-side proxy for end-user adoption is **ciências aceitas** — the count of rule declarations that employees explicitly acknowledged (gave "ciencia"). When measured for Atento México, the result is catastrophic: out of roughly 8.000 declarations generated by the system, only 2 had been accepted. Effectively zero adoption.

The root cause sits on Atento México's side: their operation does not communicate to end users that they must log in and acknowledge declarations, and the global team is not enforcing it. From 4Shark's perspective the platform is doing its job — generating the declarations correctly. From a contract-defence perspective, exposing this number gives the México local team ammunition to escalate to global with the narrative "the system is not being used, there is no point paying for it", which is the cancellation path we want to avoid.

The decision: **do not surface ciência-acceptance figures in the corporate report.** Build the report around volume and configuration metrics that demonstrate the platform is actively processing real money and a real operational load every month. This shifts the narrative from "are users engaging?" to "is the platform delivering operational value?".

## Objective

Generate a corporate utilization report for Atento México covering **July/2025 through April/2026**, presenting only volume, configuration, and processing metrics — never end-user engagement metrics.

## Scope

### In scope

- Extract the 7 metrics defined below across all 10 months (Jul/2025 – Apr/2026).
- Build a working XLSX with the raw monthly data plus 8 derived charts.
- Build a client-facing PPT with cover, 8 chart slides, and a consolidated data-table slide.
- Both deliverables in Spanish (client-facing, Mexican audience).

**Month-inclusion rule:** a month is included in the report only when **both quincenas (1RA and 2DA) have been exported**. A month with a single quincena would dip the curves and misrepresent activity. This is the same rule that kept April out of the previous run and is what keeps May/2026 out of this one (only 1RA_QNA_MAYO_2026 is exported so far).

### Out of scope

- Any ciência / declaration / acceptance / login / session-monitoring metric.
- Any end-user engagement metric (last login distribution, active users, declaration acknowledgement rate, statement opens, etc.).
- Comparing Atento México against other clients.
- Forecasting / projection slides.

## Metrics

The deliverable reports nine values per month, organised in eight charts plus a consolidated data table. Every metric is **platform-side activity** — what the platform processed or how it was configured — not end-user behaviour.

| # | Metric (ES) | What it counts | Why it's defensible to show |
|---|-------------|----------------|-----------------------------|
| 1 | Pagos | Distinct compensation payment batches closed in the month | Operational cadence — expected to be small and stable (biweekly batches) |
| 2 | Valor (MXN) | Sum of money paid through the platform in the month | Scale of financial activity processed — the headline "the platform moves real money" |
| 3 | Usuarios | Distinct users who received payment in the month | Active payee base |
| 4 | Planos | Distinct compensation plans that paid out in the month | Operational complexity — Atento runs roughly 130 plans per month |
| 5 | Reglas | Distinct rules used in calculations during the month | Configuration depth |
| 6 | Variables | Distinct variables referenced by those rules | Configuration breadth |
| 7 | Indicadores | Indicator records loaded for the month | Data-intake volume |
| 8 | Indicadores por Usuario (derived) | `Indicadores ÷ Usuarios` | Average data points per user — XLSX only, derived in the spreadsheet, not queried |

## Data extraction approach

All data lives in the **multi-tenant** `app` Rails backend. Atento México is identified by `company_id = 1318` — every query MUST filter by this company ID to isolate Atento México's data from other tenants on the same deployment. Extraction runs via Rails console on that instance, accessed through `bin/ecs run`.

**The queries below are VALIDATED against the live schema (Rails 8.1) and cross-checked against the previous deck — all 7 metrics reproduce the deck values exactly across the full Jul/2025–Apr/2026 series.** They supersede the original skeletons, which used non-existent columns (`closed_at`, `total_amount`, `user_id`, `payments.plan_id`, `rules.company_id`/`plan_id`, `indicators`). Key corrections:

- **Month = competency**, derived from `period.starts_at` (a payment `belongs_to :period`; periods are biweekly, ~2 per month) — NOT a payment timestamp.
- **Money column is `money`** (decimal 28,6); **paid user is via `user_payments.user_id`** (the `payment.owner_id` is the batch owner, not the payee).
- **Pagos/Valor** filter `Payment` by status **"final and up"**, excluding the error states `failed` and `integration_error` → `with_status(:final, :exporting, :exported, :integrating, :integrated, :pending_integration)`.
- **Planos** come from `commissions` (`commission.plan_id`); **Reglas/Variables** come from the *paying plans'* configuration (`plan → incentives → rules`, `plan → plan_variables → variables`) — the fired-rule count via `commissionings` is ~half and is the wrong metric.
- **Indicadores** = the `Indicator` model, which maps to the **`modifiers`** table (`self.table_name = :modifiers`), grouped by `compiled_at`.
- Rails 8.1 requires raw SQL in `group`/`order`/`count` to be wrapped in `Arel.sql(...)`.

Shared setup (run once at the top of the console session):

```ruby
company_id     = 1318
start_date     = Date.new(2025, 7, 1)
end_date       = Date.new(2026, 5, 31) # extend the end boundary to add a new month
paid_statuses  = %i[final exporting exported integrating integrated pending_integration]
month_expr     = Arel.sql("DATE_TRUNC('month', periods.starts_at)")
payments_scope = Payment.for_company(company_id).with_status(*paid_statuses)
```

**Month-inclusion rule still applies** — only add a month once BOTH quincenas are exported (Pagos for that month reads 2). Collect the result hashes into a working text file and paste into the XLSX `Datos` sheet — no auto-generated extraction script.

### Metric 1 — Pagos (count of payment batches per competency month)

```ruby
payments_scope.joins(:period).where(periods: { starts_at: start_date..end_date }).group(month_expr).order(month_expr).count
```

### Metric 2 — Valor (MXN) (sum paid per month)

```ruby
payments_scope.joins(:period).where(periods: { starts_at: start_date..end_date }).group(month_expr).order(month_expr).sum(:money)
```

### Metric 3 — Usuarios (distinct users paid per month, via `user_payments`)

```ruby
UserPayment.joins(payment: :period).merge(payments_scope).where(periods: { starts_at: start_date..end_date }).group(month_expr).order(month_expr).distinct.count(:user_id)
```

### Metric 4 — Planos (distinct plans that paid out per month, via `commissions`)

```ruby
Commission.joins(payment: :period).merge(payments_scope).where(periods: { starts_at: start_date..end_date }).group(month_expr).order(month_expr).distinct.count(:plan_id)
```

### Metric 5 — Reglas (rules configured in the paying plans, per month)

Two-step: per-month set of paying plans, then distinct rules across those plans' incentives (`plan → incentives → rules`). Suppress the large intermediates with `; nil`.

```ruby
plan_pairs = Commission.joins(payment: :period).merge(payments_scope).where(periods: { starts_at: start_date..end_date }).distinct.pluck(month_expr, :plan_id); nil
plans_by_month = plan_pairs.group_by(&:first).transform_values { |rows| rows.map(&:last).uniq }; nil
plans_by_month.transform_values { |plan_ids| Rule.joins(incentive: :plans).where(plans: { id: plan_ids }).distinct.count }.sort.to_h
```

### Metric 6 — Variables (variables configured in the paying plans, per month)

Reuses `plans_by_month` from Metric 5 (`plan → plan_variables → variables`).

```ruby
plans_by_month.transform_values { |plan_ids| Variable.joins(:plans).where(plans: { id: plan_ids }).distinct.count }.sort.to_h
```

### Metric 7 — Indicadores (modifier/indicator records loaded per month)

The `Indicator` model reads the `modifiers` table; group by `compiled_at`.

```ruby
indicator_month = Arel.sql("DATE_TRUNC('month', compiled_at)")
Indicator.for_company(company_id).where(compiled_at: start_date.beginning_of_day..end_date.end_of_day).group(indicator_month).order(indicator_month).count
```

### Metric 8 — Indicadores por Usuario (derived)

Computed in the XLSX, not queried — `Indicadores ÷ Usuarios` per month.

- [ ] Confirm the closing-timestamp column on `Payment`, the money column, and the join shape between `Plan ↔ Rule ↔ Variable`.
- [ ] Adjust the query skeletons above with the validated names.

### Phase 2 — Extract the full period (Jul/2025 – Apr/2026)

- [ ] Run each of the 7 grouped queries — each returns a hash of `month => value` covering all 10 months in one shot.

## Risks

| Risk | Impact | Mitigation |
|------|--------|------------|
| Forgetting the `company_id = 1318` filter on a query | Critical — pulls every tenant's data; numbers become meaningless | Every query in this plan includes the filter; Phase 1 confirms the company column exists on each model; sanity-checks in Phase 2 catch obviously inflated results |
| Atento México reads "platform usage" as "end-user engagement" and asks for that specific cut | Critical — opens the ciência conversation | Be ready with the narrative: this report tracks platform operational throughput; end-user engagement is an operational topic (training, communication on their side) and not a system metric |
| Extracted data surfaces a clear anomaly (e.g., a dip in Usuarios or Valor in one month) | Critical — would weaken the narrative | Phase 2 sanity-checks catch outliers before the deliverable is built; if anomaly is real, decide with engineer whether to ship anyway with context, or hold the report |
| Schema knowledge gap — query skeletons here use conventional names that may not match the live schema | Medium — wrong column produces wrong number | Phase 1 dumps `column_names` for every model before any metric runs; queries only execute after the engineer confirms the names |
| Chart proportions break with 10 data points (axes overflow, legend overlaps) | Low — visual quality only | Phase 4 visual review pass; adjust label rotation / chart size if needed |
