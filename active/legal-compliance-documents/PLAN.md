## 1. Context & Scope

Danilo assembled ~16 `.docx` compliance/policy documents (copied from the internet and hand-corrected, pre-AI) in `~/Downloads/4Documents/`. The work has three intertwined goals:

- **Camada 1** — remove any reference/content belonging to OTHER companies (template residue, e.g. BONUZ's product nouns "aulas/espaços/reservas", "usuário ofertante", gamification) and standardize every document into one consistent, signable legal format.
- **Camada 2** — make every statement reflect 4Shark's REAL practices (no invented controls; validate each technical claim in code/infra/runbooks or with the engineer). Placeholders (`[DD/MM/AAAA]`, names, razão social/CNPJ) are deferred to the END.
- **Public privacy policy** — separate sub-project: correct the LIVE published privacy policy (site 4shark.com.br via Wix → S3 PDF) and publish a corrected v2.

**Document format standard (internal policies):** signable legal document — preamble + prose (ISO 27001/27002 style, not bullet "shopping list", not overly legalistic) + "TERMO DE CIÊNCIA E COMPROMISSO" + signature block + approval block. Direction of confidentiality is **unilateral** (employees/CLT sign). Confirmed as the standard and applied.

## 2. Decisions Log (load-bearing — do not re-litigate)

| # | Decision |

| D1 | Internal policy format = "Termo de Ciência e Compromisso" (signable), ISO 27001/27002-style prose. Confirmed standard. |

| D3 | **Controller/operator (LGPD): 4Shark = OPERADORA; controladora = a empresa contratante** (it decides which data is processed and why). For end-user data this is clear and does not need a lawyer. The original's "A 4SHARK é a controladora" was an untruth → corrected. |
| D4 | Data-subject deletion in the policy: 4Shark does NOT erase on the user's unilateral request — request is **routed to the contracting company (controller)**, who decides; retention for legal obligation/defense of claims may apply. | D5 | **No deadlines** in documents — use "no menor prazo possível". Only state a deadline when legally mandatory. (Removed "15 dias"/"10 dias".) |
| D6 | "Última atualização" date is **NOT** an LGPD requirement → **removed** from the public v2 (a date is versioning best-practice, not a commitment, but engineer chose to remove). Trivially reversible. |
| D7 | App release strategy = **Strategy D** (force re-acceptance of everyone). NOT versioning — just **deactivate the old document + create a NEW record**. LGPD mandates no notification channel; art. 8 §6 / 9 §2 trigger only for consent-based processing with incompatible purpose change (not our case). The in-app re-acceptance gate notifies each end-user at login — no dependency on admins cascading. |
| D9 | **Multi-country = per-country documents** (one `legal_document` per `country_id`, enforced by schema): common factual BASE + per-country legal layer (applicable law, rights, authority, role terms) + local language. | D11 | **Storage of legal docs = Git, markdown as source of truth** (version control, diff, PR-as-approval-gate, AI-friendly, feeds the pandoc+WeasyPrint PDF pipeline). Drive/Word NOT canonical. **Versioning = git history + tags** (no manual `vN` files). Rendered PDF/docx = **build artifacts** (regenerable from any tag), not committed as canonical. **Drive holds only the LATEST rendered `.doc`** (non-technical sharing); old renders not archived there. **Legal proof of "what was published/accepted at time X" = git tag + deterministic pandoc rebuild** (engineer chose this over a separate immutable per-version archive). ### WS2 — App release of v2 (Strategy D) — DONE (released + rolled out)
Goal: every user re-accepts the v2 on next login; new users see only v2; v1 acceptance audit preserved; **the acceptance screen shows ONLY the documents the logged-in user has not signed yet.**

**Pre-existing bug found (engineer flagged):** the acceptance screen lists ALL country documents, not just the user's pending ones. The "not-accepted" filter exists only as the boolean gate `pending_legal_documents_acceptance?` (`user.rb:379-388`); it is NOT applied to the list shown. The screen's data comes from `LegalDocumentScope` which filters by country only (`scope.where(country_id: user.state.country_id)`), and the frontend (`legal-document-acceptance.component.ts:78-94`) renders every node and requires ALL checkboxes. So a user who already signed doc A but not B is shown both and forced to re-check A. (`accept_legal_documents` does `find_or_initialize_by` and skips persisted ones, so data isn't duplicated — but the UX is wrong.)

The two needed filters solve different cases and BOTH are required:
- **pending-for-this-user** (active AND not-accepted-by-user) applied to the **acceptance-screen list** → each user sees only what they still must sign (the engineer's point).
- **active** (retire v1) → a NEW user does not receive the obsolete v1.

Decisions: only `disabled_at` column (inherits `enabled`/`disabled`/`enable`/`disable` from `ApplicationRecord`); "pending for this user" lives on `User#pending_legal_documents`, reused by the gate, the screen scope, and `accept_legal_documents`; **filter = correlated `NOT EXISTS`, NOT a JOIN** (engineer's call — `legal_document_acceptances` is huge: 2 prod envs × ~150k users × N docs = 300k+; `legal_documents` is tiny ~100). `NOT EXISTS` hits the unique index `(legal_document_id, user_id)` `schema.rb:1028`. The `legalDocuments` resolver is used ONLY by the acceptance screen (safe to narrow).
