### GENERATED ALWAYS AS IDENTITY and SQL*Loader

Oracle's GENERATED ALWAYS AS IDENTITY columns reject any attempt to INSERT
an explicit value:

"For a GENERATED ALWAYS AS IDENTITY column, explicit insertion of a value
 is not allowed."

This means SQL*Loader (sqlldr) with a data file that contains the PK column
will fail with ORA-32795 if the column is GENERATED ALWAYS.

### Workaround: ALTER TABLE to GENERATED BY DEFAULT

The documented technique is to temporarily change the column definition:

Step 1 — Change to BY DEFAULT to allow explicit values:
  ALTER TABLE target_table
    MODIFY id_column GENERATED BY DEFAULT AS IDENTITY;

Step 2 — Run SQL*Loader with the data file that includes the PK values

Step 3 — Revert to GENERATED ALWAYS and reset the sequence high water mark:
  ALTER TABLE target_table
    MODIFY id_column GENERATED ALWAYS AS IDENTITY (START WITH LIMIT VALUE);

"START WITH LIMIT VALUE" tells Oracle to set the sequence to the maximum
existing value + 1, preventing collisions on subsequent INSERTs.

### Identity Sequences in Data Pump

When expdp exports a table with an identity column, it exports the column
definition. When impdp imports it, Oracle creates a new sequence with a
different internal name (Oracle generates sequence names like ISEQ$$_...).

"The sequence associated with an identity column is always created with
 CACHE 20 (the default). The cache size is not exported; it is always reset
 to the default on import."

Known issue in Oracle 12.1: identity column sequences were not always
restarted to MAX+1 after import (a known bug). This was fixed in Oracle 12.2.

Data Pump works at the schema/database level and is the correct tool when:
  - Moving entire schemas (vs selective table migration with SQL*Loader)
  - Cross-version migrations within the same Oracle version family
  - The target is a fresh environment (impdp handles DDL + data together)

### AUTO_INCREMENT behavior with explicit values

"For a column with an AUTO_INCREMENT attribute, any row that has the
 column set to 0, NULL, or not set at all causes an automatic value to
 be generated. Otherwise, the value is used as-is."

MySQL does NOT require a special mode (like SQL Server's IDENTITY_INSERT)
to insert explicit PK values. The sequence automatically adjusts to
MAX(column)+1 after import.

### CHARACTER SET clause

"[CHARACTER SET charset_name]
 The character set of the data in the file."

Example:
  LOAD DATA INFILE '/path/file.csv'
    INTO TABLE target_table
    CHARACTER SET utf8mb4
    FIELDS TERMINATED BY ',' ENCLOSED BY '"'
    LINES TERMINATED BY '\n'
    (col1, col2, col3);

### MySQL 8.0 collation change (utf8mb4)

Dev docs note for 8.0.1+:
  "The default character set is utf8mb4 and the default collation for
   utf8mb4 changed from utf8mb4_general_ci (MySQL 5.7 and earlier) to
   utf8mb4_0900_ai_ci."

This can cause character comparison errors ("Illegal mix of collations")
when cross-version migrating between MySQL 5.7 and 8.0 tables.

### COPY FROM and GENERATED ALWAYS AS IDENTITY

PostgreSQL docs (COPY reference):

"For identity columns, the COPY FROM command will always write the column
 values provided in the input data, like the INSERT option OVERRIDING
 SYSTEM VALUE."

This means COPY FROM implicitly overrides the sequence for GENERATED ALWAYS
columns — no special flag needed. The sequence is NOT automatically reset;
the DBA must reset it manually after import.

### Sequence reset post-COPY

Standard post-import pattern:
  SELECT setval(
    pg_get_serial_sequence('schema.table', 'id'),
    MAX(id)
  )
  FROM schema.table;

For GENERATED ALWAYS AS IDENTITY (using sequences underneath):
  SELECT setval(
    pg_get_serial_sequence('table', 'column'),
    (SELECT MAX(column) FROM table)
  );

### INSERT with GENERATED ALWAYS AS IDENTITY (not COPY)

For INSERT (not COPY):
  -- WRONG - fails with ERROR: cannot insert into column "id"
  INSERT INTO table (id, col) VALUES (42, 'val');

  -- CORRECT
  INSERT INTO table (id, col)
  OVERRIDING SYSTEM VALUE
  VALUES (42, 'val');

  -- GENERATED BY DEFAULT allows direct INSERT without override
  INSERT INTO table (col) VALUES ('val');  -- sequence used
  INSERT INTO table (id, col) VALUES (42, 'val');  -- explicit value allowed
