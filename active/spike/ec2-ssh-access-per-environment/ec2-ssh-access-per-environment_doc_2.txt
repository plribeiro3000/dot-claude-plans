Source: Xebia blog — "Fine-Grained EC2 Access With SSM, IAM Identity Center, And Tags"
URL: https://xebia.com/blog/ssm-startsession-tags/
Fetched: 2026-07-21

Summarized mechanism (deny-based, per-user rather than per-environment, included as a second,
independent technique for the same family of problem — scoping who can StartSession on which
instance via tags):
"We tag each EC2 instance with a User tag and ensure that users can only start a session on
instances where that tag matches their username."

Policy shape: an explicit Deny on ssm:StartSession when the instance carries a User tag whose
value does not match the caller's identity, using a condition of the form:
"StringNotLike": { "aws:userid": ["AROA*:${ssm:resourceTag/User}", ...] }

The article separately notes a companion Deny that blocks ec2:CreateTags / ec2:DeleteTags on the
User tag itself, so a caller cannot re-tag an instance to grant themselves access — relevant if
4Shark ever adopts tag-conditioned SSM policies, since the Client tag already on every Mongo
instance (see SPIKE.md Finding 1) would need the same tag-immutability protection to remain a
trustworthy access boundary.
