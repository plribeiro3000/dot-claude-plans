# SPIKE — Claude Code Token/Cost Control for a Heavy Claude Max Desktop User

## Investigation question

The engineer runs the Claude Code **desktop app** on macOS under the **Claude Max $200/month plan** and regularly exhausts the plan's usage limits, buying extra usage to keep working. Two tracks were investigated:

1. Can some work be offloaded to ChatGPT/OpenAI (via a separate tool, a router pointed at Claude Code, or an MCP-based delegate) to reduce Claude token consumption, and is that actually cheaper?
2. Can a second Claude account be run/switched to for overflow capacity, what mechanisms exist for that on the desktop app specifically, what does Anthropic's policy say about multiple accounts, and how can spend be monitored/capped across the setup?

A structural cross-cutting question was folded in: is there a cheaper fix that isn't either track (model switching, prompt caching, a higher plan tier)?

**Revision 1 — the question was refined after the first pass.** Cheaper-model routing (Haiku/Sonnet aliases) is already solved on the engineer's side via their own harness setup and is NOT the open question. The actual trigger for hitting the Max limit is running 4–5 simultaneous Claude Code sessions, 12–15 hours/day, where most of the work genuinely requires Opus-class reasoning — real DevOps/infrastructure work, for example a zero-downtime migration of a 300GB RDS database. The engineer's goal is to keep the Claude Code DESKTOP APP and everything built into it — `CLAUDE.md`, hooks, custom subagents, skills, docs — while having the model underneath be swappable to a different backend for overflow capacity, without re-porting that "intelligence" into a different tool (the ChatGPT app was tried and found to import only part of it — no docs, no hooks). **Track 3 investigates this corrected question directly.** Findings F1–F17 (the original two tracks) are retained below unchanged; F18–F25 address Track 3.

**Revision 2 — the engineer has decided against per-token overflow (OpenRouter, Bedrock, Vertex) and is going with the second-account, flat-rate path (Track 2a).** The open question is now purely OPERATIONAL: when the Max quota on account A is exhausted mid-day, can the engineer log out, log into a second account B, and CONTINUE the in-progress work — specifically, do the 4–5 currently-open conversations survive the switch and become resumable under account B? **The "Track 2 operational" section (F26 onward) answers this**, grounded in Claude Code's own session-storage and Remote-Control documentation.

**Revision 3 — a follow-up, narrower question on `--resume` mechanics specifically.** Given the account-switch plan depends entirely on resuming local conversations, the engineer asked for precise clarification of how `claude --resume` behaves: whether it hands off to the desktop app or stays in the terminal, whether it resumes one conversation or all open ones, how the picker scopes/lists sessions, and whether resuming replays the full transcript (with token-cost implications) or a summary. The engineer also asked explicitly for community/social reports (Reddit, GitHub issues, forums) alongside official docs. **Question 8 in the Track 2 operational section (F33 onward) answers this, combining official documentation with clearly-labeled community bug reports.**

All facts below were verified against sources fetched in July 2026 — training-cutoff knowledge (January 2026) was treated as unreliable and not used except where explicitly marked.

**Evidence:** The Codex CLI README, fetched directly, describes it as "a coding agent from OpenAI that runs locally on your computer," distributed under the Apache-2.0 license. **Significance:** Codex CLI is a genuinely separate tool from Claude Code — it runs as its own terminal process with its own auth, so nothing about it interacts with or reduces Claude Code's usage counters directly. The offload is behavioral: the engineer manually decides which task goes to which tool. It works with a ChatGPT subscription (fixed monthly cost, own usage caps) or pay-per-token via OpenAI's API (metered, no subscription needed).

### Finding 3 (F3): Anthropic explicitly does not support routing Claude Code to non-Claude models through any gateway

**Evidence:** Two independent official doc pages carry the same sentence. From the gateway overview: "If your organization already runs an LLM gateway or API gateway, you can use it instead. Anthropic doesn't endorse, maintain, or audit other gateway products, and doesn't support routing Claude Code to non-Claude models through any gateway." From the "Other LLM gateways" reference page: "Any gateway that exposes a supported API format works. Anthropic doesn't endorse, maintain, or audit third-party gateway products, and doesn't support routing Claude Code to non-Claude models through any gateway."

**Source:** code.claude.com/docs/en/gateways (fetched 2026-07-23); code.claude.com/docs/en/llm-gateway (fetched 2026-07-23).

**Significance:** This directly answers the engineer's question about `claude-code-router` / LiteLLM-style proxying: the mechanism (`ANTHROPIC_BASE_URL` pointed at a translating gateway) is technically reachable — Claude Code just sends HTTP requests to whatever base URL is configured, and a gateway that speaks the Anthropic Messages API format on the wire can translate to GPT/Gemini/etc. on the backend — but Anthropic states plainly this is not a supported use case, and the gateway product itself (not Anthropic) is responsible for translation correctness, feature pass-through as Claude Code evolves, and any breakage. This is a statement of non-support, not a technical block or a ToS prohibition — the two are different categories and the doc does not conflate them. **Track 3 (F20/F21) shows OpenRouter itself repeats this same non-support boundary for non-Anthropic models specifically**, which sharpens what this finding means for the corrected question.

**Verification block:** URL fetched: code.claude.com/docs/en/gateways. Verbatim quote checked: "Anthropic doesn't endorse, maintain, or audit other gateway products, and doesn't support routing Claude Code to non-Claude models through any gateway" — present in the fetched page body under "Other gateways". Second URL fetched: code.claude.com/docs/en/llm-gateway, same sentence present under "How a gateway works" / opening section.

### Finding 4 (F4): The desktop app does NOT read `ANTHROPIC_BASE_URL` or `settings.json` for gateway routing — it has its own separate mechanism

**Evidence:** From the CLI-facing gateway-connect doc's "Configure each surface" section: "The desktop app reads gateway routing from its third-party inference configuration, not from `ANTHROPIC_BASE_URL` or `settings.json`. That configuration can come from your organization or from a form in the app itself... open Help → Troubleshooting → Enable Developer Mode, which restarts the app with a Developer menu. Then open Developer → Configure Third-Party Inference and enter your gateway base URL." The desktop-specific doc confirms the mechanism is `inferenceProvider: gateway` with `inferenceGatewayBaseUrl` / `inferenceGatewayApiKey`, and requires "The gateway must implement the Anthropic Messages API: `POST /v1/messages` with streaming and tool use is required."

**Source:** code.claude.com/docs/en/llm-gateway-connect (fetched 2026-07-23); claude.com/docs/third-party/claude-desktop/gateway (fetched 2026-07-23).

**Significance:** This is the direct, current answer to "does the desktop app support a router/proxy today?" — yes, but through a completely different configuration surface than the CLI (a hidden Developer Mode menu, not an environment variable or `settings.json`), and the gateway must speak Anthropic's own Messages API on the wire regardless of what model answers behind it. A side effect the same doc states explicitly: "With the gateway configuration active, the desktop app runs sessions on your local machine only: the environment picker doesn't offer SSH sessions or Anthropic-hosted cloud environments, and Remote Control is unavailable." This is a real capability loss for a Remote Control user, not a hypothetical one. **This mechanism is the same one Track 3 evaluates for OpenRouter and for Bedrock/Vertex** — the desktop app's gateway path is a single, shared mechanism regardless of which backend sits behind it.

**Verification block:** URL fetched: code.claude.com/docs/en/llm-gateway-connect. Verbatim quote checked: "The desktop app reads gateway routing from its third-party inference configuration, not from ANTHROPIC_BASE_URL or settings.json" — present under "Configure each surface → Desktop app". Second quote "the environment picker doesn't offer SSH sessions or Anthropic-hosted cloud environments, and Remote Control is unavailable" — present in the same section, same page.

### Finding 5 (F5): Using a gateway credential (not just a base URL) turns off the Max subscription and switches to per-token billing

**Evidence:** "When developers connect through a gateway with a gateway credential, usage is billed to your organization's provider account at API rates, and their claude.ai subscriptions aren't used or charged. Setting `ANTHROPIC_AUTH_TOKEN` for a gateway you run, or signing in to a Claude apps gateway with `/login`, turns off subscription login for that session... The exception is setting only `ANTHROPIC_BASE_URL`, with no gateway credential. Requests still route through the gateway, but a saved claude.ai login stays the active credential, so the subscription's usage limits and billing apply."

**Source:** code.claude.com/docs/en/gateways (fetched 2026-07-23), section "Subscriptions and gateways".

**Significance:** This is the precise, current answer to "does Max auth preclude pointing at another provider?" — no, but the two are mutually exclusive PER SESSION, not permanently: the moment a credential (`ANTHROPIC_AUTH_TOKEN`/`ANTHROPIC_API_KEY`/`apiKeyHelper`) is set, that session stops drawing from the Max plan's flat quota and starts billing per token to whoever's credential is behind the gateway. For the engineer's stated goal (offload SOME work off the Max quota to GPT), this is actually the mechanism that would work IF a translating gateway were used with an OpenAI credential behind it — the request would leave Anthropic's flat-rate quota entirely and be billed by OpenAI per token instead. But per Finding 3, Anthropic does not support this path, and no widely-adopted, audited gateway product doing Claude Code → GPT translation was found with a verified, current README (the projects found — `claude-code-router`, `claude-code-proxy` — are unofficial and unaudited by construction). **This exact mechanism is what makes Bedrock/Vertex (F23/F24) viable as overflow**: it is the SAME per-session credential switch, just pointed at an Anthropic-endorsed, Claude-model backend instead of an unsupported translator.

**Verification block:** URL fetched: code.claude.com/docs/en/gateways. Verbatim quote checked: "Setting ANTHROPIC_AUTH_TOKEN for a gateway you run, or signing in to a Claude apps gateway with /login, turns off subscription login for that session" and "The exception is setting only ANTHROPIC_BASE_URL, with no gateway credential... the subscription's usage limits and billing apply" — both present under "Subscriptions and gateways".

### Finding 6 (F6): `claude-code-router` is a concrete, existing multi-provider router project

**Evidence:** "Claude Code Router (CCR) is a local model gateway and control plane for coding agents... coding agents connect to CCR at `http://127.0.0.1:3456`, which then routes requests to your selected provider and model based on configured rules." Supported providers per the fetched README summary include "OpenAI (Chat/Responses), Anthropic (Messages), Google Gemini, OpenRouter, DeepSeek, SiliconFlow, Moonshot/Kimi, Mistral, Z.AI, Bailian, Custom compatible endpoints," with deployment options including "the desktop app (recommended for Windows, Linux, macOS) or the CLI... Docker deployment is also available."

**Source:** github.com/musistudio/claude-code-router (fetched 2026-07-23).

**Significance:** This confirms the project exists, is actively positioned for exactly this use case (routing coding-agent traffic across providers including OpenAI), and offers its own desktop app as the control surface for configuring routing rules — this is a DIFFERENT desktop app (the router's own GUI) than the Claude Code desktop app itself; it is not a plugin inside Claude Code's desktop app. It is a third-party, Anthropic-unaudited project (per Finding 3) — nothing in the fetched README states it maintains parity with Claude Code's evolving feature set, and the general risk named in the official docs (a separately-maintained gateway needing its "forwarding rules updated as headers and fields change with each release") applies to it by the same logic Anthropic states for any non-Claude-apps-gateway product.

**Verification block:** URL fetched: github.com/musistudio/claude-code-router. Verbatim quote checked: "coding agents connect to CCR at http://127.0.0.1:3456" and the desktop/CLI/Docker deployment line — both present in the WebFetch-returned summary of the repository content.

### Finding 7 (F7): MCP-based delegation servers exist and let Claude Code call out to GPT/other models mid-session

**Evidence:** The PAL MCP server README states it is "a Model Context Protocol server that enables AI tools like Claude Code, Gemini CLI, and Codex CLI to orchestrate multiple AI models within single conversations," letting the primary tool "delegate tasks to other models (GPT, Gemini, O3, etc.) while maintaining conversation context across all interactions." Setup requires "Python 3.10+, Git, and `uv` package manager" plus "API keys from at least one provider: OpenRouter, Gemini, OpenAI, Azure OpenAI, X.AI, DIAL, or local Ollama."

**Source:** github.com/BeehiveInnovations/pal-mcp-server (fetched 2026-07-23).

**Significance:** This is the concrete answer to the MCP-delegation sub-question — such a server exists, is set up locally (Python/uv, not a hosted service), and requires the engineer's own OpenAI (or other provider) API key. Economically, this still consumes Claude tokens for the orchestration turns (the tool-call request/response round-trip through Claude Code itself), and the delegated model's own output is billed separately to whatever API key is configured — this is additive complexity for a partial offload, not a clean binary swap.

**Verification block:** URL fetched: github.com/BeehiveInnovations/pal-mcp-server. Verbatim quote checked: "enables AI tools like Claude Code, Gemini CLI, and Codex CLI to orchestrate multiple AI models within single conversations" and "delegate tasks to other models (GPT, Gemini, O3, etc.) while maintaining conversation context" — both present in the WebFetch-returned README summary.

### Finding 8 (F8): Current API pricing — Claude Sonnet/Opus vs GPT-5.5/5.6, and where prompt caching fits

**Evidence:** From Anthropic's official pricing page: Claude Sonnet 4.6 is "$3 / MTok" input, "$15 / MTok" output; Claude Opus 4.8 is "$5 / MTok" input, "$25 / MTok" output; Claude Haiku 4.5 is "$1 / MTok" input, "$5 / MTok" output. Prompt caching: "Cache read (hit) — 0.1x base input price," meaning "A cache hit costs 10% of the standard input price." For GPT, per a WebSearch summary of OpenAI pricing pages (not independently re-fetched): "GPT-5.5 (Latest Flagship - April 2026)... priced at $5.00 per 1 million input tokens and $30.00 per 1 million output tokens," with GPT-5.6 Terra at "$2.50/$15" and Luna at "$1/$6."

**Source:** platform.claude.com/docs/en/about-claude/pricing (fetched 2026-07-23, Anthropic figures); the GPT figures are UNVERIFIED-SEARCH (multiple aggregator sites, not OpenAI's own pricing page, so treated as directional only).

**Significance:** At the API level, comparable-tier Claude and GPT models are roughly the same order of magnitude per token as of July 2026 (Sonnet 4.6 $3/$15 vs GPT-5.6 Terra $2.50/$15; Opus 4.8 $5/$25 vs GPT-5.5 $5/$30) — API-to-API, offloading to GPT is not obviously cheaper per token for comparable capability. **Critically for the corrected question (Track 3): there is no GPT-5.x model priced or positioned as Opus-equivalent for the hardest reasoning tasks** — GPT-5.5 at $5/$30 sits at Opus 4.8's input price but a higher output price, and neither this pricing table nor any source found in this research asserts GPT-5.x matches Opus on the kind of correctness-critical infra reasoning (a 300GB zero-downtime RDS migration) the engineer named. The economics that matter are therefore NOT "GPT tokens are cheaper than Claude tokens" — they are (a) the Max plan's $200 flat rate already amortizes a very large volume of Claude tokens before the per-token API rate would ever apply, so ANY per-token billing (Claude API overflow OR a GPT-side offload) is a worse per-token deal than staying inside the Max quota, and (b) a second flat-rate ChatGPT subscription ($20 Plus / $100 Pro-5x / $200 Pro-20x) buys a SEPARATE flat-rate quota, similar in shape to buying a second Claude Max seat.

**Verification block:** URL fetched: platform.claude.com/docs/en/about-claude/pricing. Verbatim quotes checked: "$3 / MTok" / "$15 / MTok" for Sonnet 4.6, "$5 / MTok" / "$25 / MTok" for Opus 4.8, "0.1x base input price" for cache reads — all present in the fetched model-pricing table. GPT figures are UNVERIFIED-SEARCH and not independently re-fetched from an OpenAI primary source; flagged accordingly and not used alone to sustain the "roughly comparable" claim without the Anthropic-side figures anchoring it.

### Finding 9 (F9): `CLAUDE_CONFIG_DIR` isolates CLI config/credentials per directory — documented for the CLI, not stated for the desktop app

**Evidence:** Per official docs (via WebSearch summary of code.claude.com pages): "`CLAUDE_CONFIG_DIR` is an environment variable that specifies where the wizard writes settings configuration files like `settings.json`... By default, configuration files are stored in `~/.claude/`... when `CLAUDE_CONFIG_DIR` is set, the settings are written to `$CLAUDE_CONFIG_DIR/settings.json` instead... the `.credentials.json` file lives under that directory instead of the default location." Separately, a fetch of the settings doc returned: "Environment variables applied to every session and to subprocesses Claude Code spawns from it," with no explicit desktop-vs-CLI distinction stated anywhere found. Notably, the Amazon Bedrock doc (fetched directly, F23) confirms the same directory is used regardless of backend: "The wizard writes to `~/.claude/settings.json`, or to `$CLAUDE_CONFIG_DIR/settings.json` when `CLAUDE_CONFIG_DIR` is set" — the identical sentence appears verbatim in both the Bedrock and Vertex docs. **This finding is superseded/refined for the operational question by F28 and, more sharply, by F40 below**, which shows `--resume` itself does not honor `CLAUDE_CONFIG_DIR` at all.

**Source:** WebSearch summary of code.claude.com official docs (not independently re-fetched for this specific variable page; the settings.json `env` block behavior is separately WebFetch-confirmed at code.claude.com/docs/en/settings, fetched 2026-07-23; the Bedrock/Vertex cross-reference is WebFetch-confirmed at code.claude.com/docs/en/amazon-bedrock and code.claude.com/docs/en/google-vertex-ai, fetched 2026-07-23).

**Significance:** `CLAUDE_CONFIG_DIR` is an environment variable — it only takes effect in the process environment the `claude` binary is launched from. A terminal session with `export CLAUDE_CONFIG_DIR=...` before running `claude` works cleanly (confirmed by multiple community sources: madewithlove.com's article shows `alias claude-mwl='CLAUDE_CONFIG_DIR="/Users/mike/.claude-mwl" claude ...'`). A macOS GUI app launched from Finder/Dock does NOT inherit shell environment variables set in `~/.zshrc` unless the app is launched from a terminal or the variable is set via a mechanism macOS GUI processes read (e.g., `launchctl setenv`, which is global, not per-instance) — no source found confirms `CLAUDE_CONFIG_DIR` works for isolating two SEPARATE simultaneous desktop-app instances the way it isolates two terminal sessions. This is a genuine gap: the CLI mechanism is well-documented and battle-tested by the community; the desktop-app equivalent is NOT documented anywhere found in this research. **This is orthogonal to Track 3**: switching the MODEL BACKEND (Bedrock/Vertex/gateway) is a single-account, single-config-directory operation — it does not require `CLAUDE_CONFIG_DIR` isolation at all, since it is not a second identity, just a second credential inside the SAME `~/.claude/settings.json`.

**Verification block:** URL fetched: code.claude.com/docs/en/settings (for the general `env` block behavior); code.claude.com/docs/en/amazon-bedrock and code.claude.com/docs/en/google-vertex-ai (for the cross-reference confirming the same settings file is used). The `CLAUDE_CONFIG_DIR`-specific quotes for the CLI mechanism are UNVERIFIED-SEARCH (WebSearch summary of official pages, not independently re-fetched for that exact variable's page) — flagged accordingly; the CLI-only community usage (madewithlove.com) IS WebFetch-verified: quote "alias claude-mwl='CLAUDE_CONFIG_DIR=\"/Users/mike/.claude-mwl\" claude -e \"/color red\"'" confirmed present in the fetched article content.

**Finding 18 (F18): Hooks are executed by the Claude Code harness itself, independent of which model answers requests.** Fetched directly from the hooks reference doc: "Hooks are user-defined shell commands, HTTP endpoints, or LLM prompts that execute automatically at specific points in Claude Code's lifecycle." ### Question 6 — The practical hand-off recipe

Synthesizing F26–F31, sustained by the findings named per clause:

**What CARRIES across a same-machine, same-`CLAUDE_CONFIG_DIR` account switch (sign out of A, sign into B, nothing else changed):**
- The local transcript files themselves (F26) — they are project-directory- and session-ID-keyed, not account-keyed, so they remain on disk untouched by a credential change.
- The ability to reopen them: `claude --resume <name-or-id>`, `claude --continue`, or the interactive `/resume` picker on the CLI (F27); most likely the Desktop app's own session list for the Code tab as well, though this specific point is a strong inference rather than a directly-tested statement (F31).
- All code, files, and git state in the project directory — these were never touched by which account is logged in; they are ordinary filesystem/git objects with no Claude-account reference at all.
- `CLAUDE.md`, hooks, custom subagents, skills, and `settings.json` (established in Track 3, F18/F19/F25) — these are harness-side and project-directory-scoped, so an account swap changes nothing about them, exactly as a model-backend swap did not.

**What does NOT carry, or requires a fresh step:**
- Any Remote-Control-registered / claude.ai-web-visible session state (F30) — this is server-side and bound to the account that was signed in when the Remote Control session was started. To keep phone-driven steering going under account B, the engineer would start a NEW Remote Control connection (`/remote-control` again, or `claude --remote-control`) from the already-resumed LOCAL conversation under account B — the local conversation carries over per above, but its Remote Control registration does not automatically transfer; it must be re-established under the new account's session.
- A clean, single-shot account switch: the desktop app's documented mechanism is a full sign-out/sign-in cycle (F29), not a `/login`-while-already-signed-in shortcut (which a related, closed-as-not-planned bug shows is unreliable). The engineer should expect to explicitly sign out before signing in as the second account.

**The one condition that must hold for any of this to work:** the second account's session must run against the SAME, DEFAULT `~/.claude` storage location — leaving `CLAUDE_CONFIG_DIR` unset entirely is the safest reading once F40 is factored in, rather than merely "the same non-default value across accounts" (see F40) — rather than a second, isolated config directory of the kind used for the CLI "per-profile" multi-account pattern (F9, F12). That isolation pattern's entire purpose is to give each profile its OWN separate `projects/` transcript tree (F28), which would be the wrong choice here, since it defeats exactly the continuity the engineer wants.

**Finding 40 (F40) — UNVERIFIED-SEARCH (community bug report, GitHub issue #16103, closed as not-planned, not an Anthropic official statement): `--resume` itself ignores `CLAUDE_CONFIG_DIR` and only ever searches the DEFAULT `~/.claude/projects/` location — even when sessions were correctly saved to a non-default `CLAUDE_CONFIG_DIR`.** The issue reports: "Sessions are saved correctly to `$CLAUDE_CONFIG_DIR/projects/...` [but] Sessions cannot be resumed via `claude --resume SESSION_ID` from the CLI... `--resume` only searches `~/.claude/projects/`, ignoring the `CLAUDE_CONFIG_DIR` environment variable," producing the error `No conversation found with session ID: SESSION_ID`. **Synthesis of Question 8, directly answering the engineer's four sub-questions:**

1. **Terminal vs. desktop hand-off:** `claude --resume` run in a terminal stays in the terminal — it does not open or hand off to the desktop app (F33). The desktop app has its own separate sidebar-click mechanism for the same underlying idea, and interop exists only through the explicit `/desktop` command that hands a CLI session TO the desktop app (one-directional, not what `--resume` does).
2. **One vs. all:** Every invocation resumes exactly ONE conversation — `--continue` auto-picks the most recent one, `--resume` opens a picker to choose one, `--resume <id>` goes straight to one (F34). There is no bulk "resume everything open," and no documented "finished" vs. "unfinished" status — all past sessions are equally resumable regardless of completion state.
3. **What the picker lists:** Sessions from the CURRENT project directory and worktree by default, plus anything explicitly `/add-dir`'d — not all history regardless of location, and being in the SAME working directory the session was created in is required unless the picker is manually widened with `Ctrl+A`/`Ctrl+W` (F35), corroborated by community reports of confusing "invalid or expired" errors when this scoping is not respected (F39).
4. **Full replay vs. summary, and token cost:** Resume restores the FULL transcript, not a summary (F36, official) — and a community bug report quantifies that this can carry a real, sometimes large token cost from opaque "thinking block" data specifically, up to roughly a quarter of the total resume payload in one analyzed example (F37, community). This is a genuine, documented-from-both-sides answer: officially, "full history" is restored by design; unofficially (and not contradicted by any official source), that full-history restoration has a measurable token cost the official docs do not quantify or warn about.

Two further community reports bear on RELIABILITY rather than the four questions directly: sessions can go missing from the picker due to a stale index, with a documented `--resume <session-id>`-from-the-file fallback (F38), and `--resume` has been reported to ignore a non-default `CLAUDE_CONFIG_DIR` entirely (F40) — which sharpens the Question 6 recipe toward leaving `CLAUDE_CONFIG_DIR` unset for the account-switch plan specifically. No community report was found describing an interaction between `--resume` and account logout/login directly — the account-switch scenario itself was not something any fetched community source tested; F26/F27/F40 remain the basis for that answer, combining an official structural fact (transcripts are local and directory-keyed) with a community-reported caveat (resume's own directory search is hardcoded to the default location, regardless of `CLAUDE_CONFIG_DIR`).
