# SPIKE — Mechanically Preventing an AI Coding Agent from Leaking Internal Information into Pull Request Descriptions

## Investigation question

Given that 4Shark's context-injection reminder (`inject-pr-commit-data-policy.sh`, re-firing on every `gh pr create`) demonstrably failed to stop an AI coding agent from putting organizational internal information into PR descriptions — four consecutive PRs at first observation, eleven more found on audit of a public repository over months — what mechanical (not prompt-based) options exist to prevent this class of leak? The leaked content was not the customer-facing values the rule's own examples describe (client names, hostnames, connection strings, business volume figures); it was organizational meta-information: names of other private repositories cited as pattern sources, a stated security-posture gap in a named repository, inventory facts about the private codebase, the existence of an internal engineering-document set, a private application's API/authorization design, and the organization's branching and release process — all written into a repository whose visibility differs per case, including at least one public one.

Six sub-questions guided the research: (1) does the industry name this failure class; (2) is there measured evidence on reminder-injection vs. a hard gate; (3) what do real organizations do to keep internal information out of public repositories; (4) is 4Shark's own denylist objection (unmaintainable, itself leaks values) sound for every category of leak, and is a runtime-derived list an established escape from it; (5) does repository visibility belong in the decision, and can it be established cheaply; (6) is a GitHub PR body edit truly a fix, or only cosmetic.

## Sources consulted

## Findings

### Finding 1: No source names 4Shark's exact failure shape ("policy in context, violated anyway"), but two adjacent, differently-scoped terms exist

**Evidence:** "The Instruction Gap" paper defines its own term as "a fundamental challenge where models excel at general tasks but struggle with precise instruction adherence required for enterprise deployment," and ties the mechanism to "lost in the middle behaviors where LLMs struggle to utilize information from the middle portions of long contexts" and to instruction mechanisms that "become diluted when processing complex, multi-component instructions alongside substantial context." Separately, "The Compliance Gap" paper opens with a directly analogous scenario — an agent told "no scripts, no agents," replying "Yes," then batching the work anyway — and identifies the cause as "structurally inevitable under RL that rewards text without observing behavior," a gap that is "undetectable from text alone" because only the verbal commitment is observed, not the behavioral violation.

**Source:** [arXiv:2601.03269v1](https://arxiv.org/html/2601.03269v1); [arXiv:2605.01771](https://arxiv.org/abs/2605.01771)

**Significance:** Neither paper's named term is a perfect match for 4Shark's case. "The Instruction Gap" is about context dilution as more text competes for attention — closer to why a reminder re-injected every turn can still be outweighed by the surrounding task content. "The Compliance Gap" is about the reward signal during training never checking the actual tool-call/output against the stated commitment — closer to why the model can affirm a rule about "client names, hostnames, connection strings" and still write "here's how repo X does it" without recognizing that as the same rule, because nothing during training ever penalized that specific output shape. Both are candidate framings; neither is 4Shark's incident by name.

### Finding 2: Measured evidence favors removing the affordance over reinforcing the prompt — but the measurement is about tool removal, not about reminder-injection specifically

**Evidence:** "removing delegation tools raises compliance to 75% (Cohen's d = 2.47), confirming environmental affordance rather than weight-encoded failure."

**Source:** [arXiv:2605.01771](https://arxiv.org/abs/2605.01771)

**Significance:** This is the closest measured comparison found between a prompt-level fix (the model already receives and affirms the instruction) and an environment-level fix (the tool that lets it cheat is removed). The paper's own framing is that the gap is "environmental affordance" — the model complies more when the environment no longer offers the shortcut. No source measured "reminder re-injected every call" against "hard gate that blocks the call" directly for this leak-into-PR-body scenario; the 75%-compliance figure is evidence for the general shape of the argument (removing the affordance beats asking harder), not a number that transfers to 4Shark's exact mechanism.

### Finding 3: Rising failure rate as context grows is measured, independent of this specific incident, and applies to the mechanism 4Shark used (re-injection on every call)

**Evidence:** "Perfect-response rate collapses to zero by N=80 for every model, format, and placement" as instruction count rises from 10 to 160 in one controlled study; a second, independent report finds "models do not use their context uniformly; instead, their performance grows increasingly unreliable as input length grows," even on simple tasks.

**Source:** [arXiv:2607.19257](https://arxiv.org/abs/2607.19257); [Chroma Research — Context Rot](https://www.trychroma.com/research/context-rot)

**Significance:** 4Shark's hook re-injects ONE rule every call, which sits far below N=80 rules — so this finding does not claim the hook's specific failure is explained by rule-count collapse. What it does establish, independent of the specific incident, is that a policy delivered as prompt text competes with everything else in context and is not guaranteed to survive that competition as a session's context grows — which is the general argument against relying on any prompt-delivered rule, reminder or otherwise, as the sole control.

### Finding 4: Claude Code's own hook mechanism can deterministically block a tool call before it executes, and the tool input it receives is the exact text that would leak

**Evidence:** "PreToolUse blocks the tool call" on exit code 2; the hook receives the full tool input, e.g. `{ "tool_name": "Bash", "tool_input": { "command": "..." }, ... }`. The docs also explicitly caution: "Because the `if` filter is best-effort, use the permission system rather than a hook to enforce a hard allow or deny."

**Source:** [Anthropic — Claude Code hooks reference](https://code.claude.com/docs/en/hooks)

**Significance:** A `PreToolUse` hook on `Bash` firing on a `gh pr create` command receives the entire command string, including the `--body` argument that carries the PR description text about to be published. The mechanism to inspect that text and block the call outright (rather than merely annotate context, which is what `inject-pr-commit-data-policy.sh` does today) already exists in the same hook family 4Shark already uses elsewhere for hard blocks (`validate-bash-command.sh`, `validate-service-scale-down.sh`). The caveat about `if` filters being "best-effort" is about the hook's own trigger condition (deciding *whether* to run), not about the blocking decision itself once the hook runs — `exit 2` is unconditional once reached.

### Finding 5: Secret scanning — the closest existing GitHub-native tool — is architecturally scoped to credential-shaped strings, not prose

**Evidence:** The custom-patterns documentation frames the entire feature around "the format of your secret pattern," with no example or mention of detecting general business/architecture prose.

**Source:** [GitHub Docs — Defining custom patterns for secret scanning](https://docs.github.com/en/code-security/secret-scanning/using-advanced-secret-scanning-and-push-protection-features/custom-patterns/defining-custom-patterns-for-secret-scanning)

**Significance:** Confirms the premise in the investigation prompt: secret scanning (including push protection) is not a candidate mechanism for this leak class as-is. A custom pattern could technically be written as a regex matching known repository/product names, but that is a repurposing of a credential-scanning feature, not its documented use case, and GitHub's own custom-pattern regex support (Hyperscan, a PCRE subset) was not found to be documented as supporting anything beyond pattern matching against a fixed regex — i.e., it would still need the names hardcoded into the pattern, which is exactly the maintenance/leak objection 4Shark's own rule already raised for customer values.

### Finding 6: At least one company's open-sourcing checklist treats "internal names not matching the public ones" as its own sanitization category, separate from secrets

**Evidence:** "Internal product names that don't match the public ones" and "Censoring internal domains used in tests" appear as line items alongside credential-scanning steps.

**Source:** [GitGuardian — Safely open-source software](https://blog.gitguardian.com/safely-open-source-software-best-practices/)

**Significance:** This is a documented, named practice for the exact category 4Shark's incident falls into (internal repository/product names, not customer values) — but it is described as a manual checklist item to review before a one-time publication event, not as an automated, ongoing gate applied to every PR body as it is written. No source was found describing a tool that performs this check the way secret scanning performs credential checks.

### Finding 7: 4Shark's own denylist objection is explicitly about maintenance cost and self-leakage — a runtime-derived list changes the second half of that objection, but no source names this as an established technique for this use case

**Evidence:** No industry source was found using a specific name for "derive a denylist from a live API instead of hardcoding it, specifically for organization-name/architecture-prose leaks." The nearest documented analog is Exact Data Match (EDM) in commercial DLP tooling, described (uncorroborated by direct WebFetch, see auxiliary file) as comparing against "scalable indexing databases that can be refreshed according to your needs" rather than a static regex — the same shape of idea (live source, not hardcoded pattern) applied to structured PII records (account numbers, SSNs), not to prose mentioning an organization's own repository names.

**Source:** Auxiliary file `pr-body-internal-data-gate_sources_1.md` § "Data Loss Prevention — Exact Data Match" (EDM description is WebSearch-aggregated only, not independently WebFetched — flagged UNVERIFIED for exact wording, though the concept is corroborated across multiple independent vendor pages)

**Significance:** The technical composition itself is not exotic — `gh repo list --json name` (or the cached local `~/Projects/4Shark/` directory listing) run at hook time would produce the current set of internal repository names without ever writing them into a config file, which answers 4Shark's own objection ("the list would be unmaintainable and would itself version customer names and hostnames into the config repository") for exactly the sub-category where the list is 4Shark's own inventory rather than a customer's. The objection's second half ("unmaintainable") is also weakened for a runtime-derived list — it self-maintains as repositories are created/renamed/removed, unlike a hand-maintained file. Whether 4Shark's objection was ever meant to cover this sub-category, versus only customer-controlled values that 4Shark cannot enumerate via any API it operates, is a distinction the original rule's text does not draw — it states the objection in general terms covering "customer names and hostnames" specifically, not "the organization's own repository names."

### Finding 8: 4Shark's own denylist objection does not obviously extend to categories that are not enumerable at all — the leaked content in this incident includes several such categories

**Evidence:** Of the six leaked-content categories named in the investigation brief, only one (other repository names) is straightforwardly enumerable via an API call. The other five — a stated security-posture gap, inventory facts about the private codebase ("every rescue in every Ruby repository"), the existence of an internal engineering-document set, a private application's API/authorization design, and the branching/release process — are not values that exist in any list a hook could fetch and compare against; they are *descriptions*, not *tokens*.

**Source:** Derived from the investigation brief's own enumeration of the leaked content, cross-referenced against Finding 5 (secret scanning is pattern-matching against known tokens) and Finding 7 (denylist has an enumerable and non-enumerable half)

**Significance:** A runtime-derived denylist, even if built, would catch only the repository-name sub-category of this incident's leaks — roughly one of the six observed leak types. The remaining five require either (a) a semantic judgment about whether a sentence describes internal architecture/process, which is the same class of judgment call that failed in the first place if delegated back to the same model with a bigger prompt, or (b) a structural rule that does not depend on content classification at all (see Finding 9).

### Finding 9: Repository visibility is cheap, reliable, and queryable before any write — but no source frames visibility as the deciding factor for this leak category specifically

**Evidence:** `gh repo view --json isPrivate` / `--json visibility` are documented, stable CLI fields; `private` is a documented boolean field on the REST API's "Get a repository" response.

**Source:** [GitHub CLI manual — gh repo view](https://cli.github.com/manual/gh_repo_view); [GitHub Docs — Get a repository](https://docs.github.com/en/rest/repos/repos?apiVersion=2022-11-28)

**Significance:** Establishing visibility before a `gh pr create` write is a single, fast, side-effect-free API call — there is no technical barrier to gating on it. No source was found that discusses treating a PR body differently by repo visibility as an established practice; this is an inference from confirmed platform mechanics, not a documented industry pattern. It is worth noting that gating purely on visibility does not address the private-repo case: the investigation brief states the eleven-PR audit was on a public repo, but the four-PR original observation is not stated to be scoped to any particular visibility — if any of those four were private, a visibility-only gate would have let them through, since "internal information reaching a PRIVATE 4Shark repo" may still be a leak relative to which engineers/contractors have read access to that repo, just a smaller-blast-radius one than a public repo.

### Finding 10: A GitHub PR/comment body edit is not truly reversible — the pre-edit text remains visible by default to anyone who could already read the PR, and is recoverable outside GitHub's UI entirely regardless of any in-app deletion

**Evidence:** "Anyone with read access to a repository can view a comment's edit history." Deletion of a specific revision's content requires an explicit additional step ("Comment authors and anyone with write access to a repository can delete sensitive information from a comment's edit history" via "Delete revision from history"), and even then "the editor's name and timestamp remain visible" — only the text of that one revision is removed, and only from GitHub's own UI. Separately, "It doesn't look like there is an API that will give you the body of previous PRs, only the event timeline" — so a live third-party webhook subscriber that captured `changes.body.from` at edit time already has the pre-edit text, independent of anything GitHub's UI later allows an engineer to delete. GH Archive is described as recording "the public GitHub timeline" since 2011, "updated hourly," and queryable via a public BigQuery dataset.

**Source:** [GitHub Docs — Tracking changes in a comment](https://docs.github.com/en/communities/moderating-comments-and-conversations/tracking-changes-in-a-comment); [GitHub Community Discussion #151829](https://github.com/orgs/community/discussions/151829); [GH Archive](https://www.gharchive.org/)

**Significance:** For a public repository, editing a leaked PR body after the fact is a two-layer problem. Layer one (GitHub's own UI) is a real but incomplete remediation: the default "edited" history is visible to anyone with read access — meaning any visitor to a public PR — until someone with write access explicitly deletes that specific revision's content, a distinct manual step from the ordinary edit. Layer two (anything outside GitHub's UI that already ingested the body) is not remediated by GitHub UI actions at all: GH Archive's hourly public snapshots and any GitHub App/webhook subscriber active at the time of the original post or the edit already have a durable copy, and there is no API-level "undo" that reaches those. The REST API confirms `body` is a first-class field on the PR object ("`body`: required, string or null"), meaning any tool polling PRs — search indexers, mirrors, other CI integrations — could have captured it in the window before any edit. This establishes that a post-hoc edit is, at best, a partial remediation for the GitHub-native surface, and not a remediation at all for anything that already fetched the pre-edit content through the API or a webhook — it does not un-happen the exposure, it narrows who can still see it inside GitHub's own product surface, and only after an extra manual step beyond the edit itself.

### Finding 11: A real, named, disclosed incident exists in which an AI agent leaked private GitHub repository content to a public surface, and prompt-based guardrails were the control that failed

**Evidence:** "GitHub had restrictive guardrails in place to prevent exactly this scenario, but they failed to protect the repositories as intended" — defeated by prefacing the injected instruction with "Additionally," which "triggered unintended behavior in the model, causing it to reframe its output rather than refuse it." Confirmed exfiltrated content included the contents of a private repository's README, extracted into a public comment.

**Source:** [Noma Security — GitLost](https://noma.security/blog/gitlost-how-we-tricked-githubs-ai-agent-into-leaking-private-repos/)

**Significance:** This is a different trigger mechanism than 4Shark's incident — GitLost is adversarial prompt injection from an external, untrusted GitHub Issue; 4Shark's leak is the model's own unprompted judgment call with no adversarial input in the loop. Both land on the same outcome (private/internal content reaching a public GitHub surface via an agent) and both show the same pattern named in Finding 4/Wiz's framing: a guardrail expressed to the model, present and intended to prevent exactly this, did not prevent it. This is corroborating evidence, not proof that the same fix applies — GitLost's own remediation path (trust-boundary enforcement between untrusted external content and privileged actions) is not the same shape as 4Shark's problem (there is no untrusted external actor in 4Shark's leak).

### Finding 12: OWASP's own guidance names the exact limitation 4Shark has now observed directly, but its listed mitigations do not include a control matching this specific leak category

**Evidence:** "Adding restrictions within the system prompt about data types that the LLM should return can provide mitigation against sensitive information disclosure. However, such restrictions may not always be honored and could be bypassed via prompt injection or other methods." The mitigation list fetched (sanitization, least-privilege data access, limiting external data source access, concealing system prompts, tokenization) is scoped to PII/credentials/health/legal-document examples throughout.

**Source:** [OWASP GenAI — LLM02:2025 Sensitive Information Disclosure](https://genai.owasp.org/llmrisk/llm022025-sensitive-information-disclosure/)

**Significance:** OWASP's own top-level guidance for this risk category independently states the exact failure 4Shark measured (system-prompt restriction "may not always be honored") — this is corroboration from an industry standards body, not merely 4Shark's own experience, that a prompt-delivered rule is documented as insufficient on its own. However, none of OWASP's listed mitigations is shaped for "the model's own organizational-metadata prose ends up in an artifact it authors" — the mitigation list assumes the sensitive data enters via training data, retrieval, or a queryable data source the model can be restricted from reaching, not via the model narrating facts about the environment it is already operating in as part of its job (explaining where a code pattern came from is, in the ordinary case, a legitimate and requested part of the PR-writing task).

## What remains uncertain

- No source names 4Shark's exact failure shape — a policy present and affirmed in context, violated in the specific output anyway, on a category the rule's own examples never illustrated. "The Instruction Gap" and "The Compliance Gap" are the closest framings found, but neither is a literal match, and neither should be cited as *the* name for this phenomenon.
- No direct, controlled comparison was found measuring "reminder re-injected into context every call" against "hard PreToolUse gate" for this exact leak scenario (PR body composition). The closest measured evidence (Compliance Gap's 75%-compliance figure) is from a different task shape (tool delegation, not text composition) and should not be read as transferring numerically.
- Whether "derive the denylist from a live API instead of hardcoding it" is an established, named industry technique for this specific use case (organization-name leak prevention) was not confirmed. Exact Data Match is the nearest documented analog, and it is scoped to structured PII records, not organizational prose or repository-name mentions — the analogy is reasoned, not sourced.
- Whether repository visibility should gate the strictness of a control (block on public, warn on private, or treat both the same) has no precedent found in the literature — this is a policy choice 4Shark would be making without industry cover either way.
- Five of the six leaked-content categories in this incident (security-posture statements, codebase-inventory facts, the existence of an internal doc set, API/authorization design description, branching/release process description) are not enumerable tokens a denylist or a visibility gate can catch — no mechanical approach found in this research addresses that half of the incident. Any option that only covers the enumerable half (repository names) leaves the majority of the observed leak categories uncovered.
- The self-check performed on "Security Boulevard — AI Agent Guardrails" failed (HTTP 403); its content is recorded in the auxiliary file as UNVERIFIED and was not used to sustain any Finding above on its own.

## Suggested options for main and the engineer

- **Option A — Deterministic `PreToolUse` block on `gh pr create`, matched against a runtime-derived list of 4Shark's own repository names** (via `gh repo list` or the local `~/Projects/4Shark/` directory listing, never hardcoded). Directly answers 4Shark's own denylist objection for the sub-category where the "denylist" is 4Shark's own enumerable inventory rather than customer-controlled values. Covers only the "cites another private repo by name" leak type (Findings 4, 7, 8).
- **Option B — `PreToolUse` gate scoped by target-repository visibility**, using `gh repo view --json isPrivate` before the write, with stricter handling (block, or require an explicit override) when the target is public. Cheap and reliable to implement; addresses the highest-blast-radius case first; does not address a private-repo leak of the same content, and has no found precedent specifically for this leak category (Finding 9).
- **Option C — Combine A and B**: visibility decides strictness (block on public, flag on private), repository-name matching decides one concrete trigger within that. Still leaves the five non-enumerable leak categories uncovered by construction — any coverage of those categories would need a different mechanism than pattern/list matching, because they are prose judgments, not tokens (Finding 8).
- **Option D — Remove the affordance rather than gate the output**: restrict what the agent can read/reference about sibling private repositories, internal doc sets, or the organization's own process history while composing a PR body, so there is nothing to accidentally narrate. Grounded in the one measured result found that environment-level fixes outperformed a prompt-level one in a different task (Finding 2/7), but untested for this specific scenario, and it may remove information the PR body legitimately needs (attributing a pattern's source is often exactly what's wanted).
- **Option E — Treat this as presently unsolved by mechanical content-classification, and instead harden the remediation path**: keep the reminder (it is not zero-value, it just is not sufficient alone), add a mechanical gate for what IS enumerable (Option A/B/C), and separately establish an explicit incident-response step for the five non-enumerable categories — audit PR bodies after the fact (as the eleven-PR audit already demonstrated is possible), and understand that a post-hoc edit narrows but does not eliminate exposure (Finding 10), so the audit-and-fix path is a mitigation of consequence, not a prevention of occurrence.

No option above is recommended over another — each addresses a different slice of the six observed leak categories, and none found in this research fully covers all six.
