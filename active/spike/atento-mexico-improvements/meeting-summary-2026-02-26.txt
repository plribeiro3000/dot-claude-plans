Sábana de Resultados Simplificada

- El reporte debe ser para un número reducido de usuarios, con la capacidad de filtrar por meses y ser generado por administradores o managers.
- Se confirmó que el reporte debe incluir solo información de pagos finalizados y aprobados, excluyendo premiaciones no aprobadas.

Sábana Completa con Tipos de Pago
Se abordó la creación de una sábana general para control financiero y auditorías.
- La sábana general consolidaría indicadores operativos y resultados de cálculo de bonos para control y auditoría, con 120 columnas activas.
- El objetivo es verificar la carga de indicadores, porcentajes y topes de bonos, permitiendo un control a nivel compañía.
- Se busca que la sábana pueda generarse en cualquier momento del proceso, no solo al final del pago, para validaciones previas.
- Se propuso unificar la información en una sola tabla, y se discutió la necesidad de diferenciar los estados de pago (parcial, premiación, compensación aprobada/no aprobada, pago aprobado/no aprobado).

Edición Masiva de Usuarios
Se analizó la necesidad de actualizar datos de usuarios de forma masiva.
- Luis explicó que el proceso actual es lento debido a la edición manual de nombres y otros datos para 20 colaboradores quincenalmente.
- Se busca una funcionalidad de carga masiva que permita actualizar usuarios existentes, similar a la carga inicial.
- Se informó que la funcionalidad de reinicio masivo de contraseñas ya existe y se ofrecerá una sesión de entrenamiento para explicarla.
- La integración futura con el sistema de nómina (book) automatizará la actualización de datos de usuario en la plataforma.

Creación y Planificación Masiva de Planes
Se examinó la creación de 130 planes mensuales y la gestión de informes.
- Luis crea 130 planes mensualmente para el cálculo de compensaciones, utilizando archivos de control para copiar y pegar la configuración.
- Se solicitó una funcionalidad de carga masiva de planes, donde un layout permitiría subir calendario, grupo, variables y tipos de pago.
- Se acordó que, por seguridad, el sistema debería rechazar el layout completo si hay errores en algún plan, en lugar de cargar parcialmente.
- Se discutió la necesidad de usar IDs de incentivos en el layout para la creación masiva de planes, ya que los nombres son propensos a errores.
- Se aclaró que el lote de informes de compensaciones genera informes individuales para cada plan, no un informe general consolidado, y que el proceso de generación de informes se separa del cálculo para optimizar el rendimiento del servidor.
