Gerenciadores de pacotes JS — Yarn vs. o resto

Análise para o app-webclient · 11 de setembro de 2026 · pergunta: continuar no Yarn ou migrar?

Recomendação: ficar no Yarn.

Vocês estão no Yarn 4.18.0 (a linha atual e mantida), e o app-webclient já tem todas as defesas de supply-chain que o aube vende como diferencial — só que num tool maduro. Trocar de gerenciador hoje não compra segurança nenhuma e adiciona risco. O aube é interessante, mas tem 3 meses de vida e a própria comunidade diz "ainda não para produção".

1. "São todos a mesma coisa?" — Não. Tem uma taxonomia aqui.

A confusão é justa, porque o marketing de todos usa as mesmas palavras. Mas eles ocupam papéis diferentes:

npm padrão
Gerenciador de pacotes

Vem embutido no Node. Máxima compatibilidade. O npm 11 (fev/2026) ganhou min-release-age nativo.

Yarn o de vocês
Gerenciador de pacotes

Linha atual é a Berry (4.x), ativa (4.18.0 em jul/2026). O Yarn 1 "Classic" está em manutenção desde 2020 — mas vocês NÃO estão nele.

pnpm alternativa madura
Gerenciador de pacotes

Store global content-addressable → ~70% menos disco. Rápido, compatível. Ganhou minimumReleaseAge em set/2025.

bun runtime, não só PM
Runtime + bundler + test + PM (em Zig)

NÃO é "um pacote de segurança". É um runtime completo que inclui um gerenciador. Adotá-lo = adotar o runtime inteiro. Muito rápido.

aube novo (2026)
Gerenciador de pacotes (em Rust)

O da newsletter. Do jdx (autor do mise). Modelo de disco tipo pnpm, lê/escreve o lockfile que você já tem. Foco em segurança e velocidade.

Bower morto
Gerenciador de pacotes (histórico)

O que o Twitter lançou (~2013), aquele "que morreu". Deprecado há anos. Não entra na conta.

Dois erros de premissa que vale corrigir

1. "O bun é um pacote de segurança que deu problema." Não. O bun é um runtime + gerenciador, e não teve incidente próprio. Os problemas de segurança que você ouviu falar são os ataques de supply-chain no registro do npm (o worm Shai-Hulud, 2025–2026) — que atingem pacotes publicados no npm e portanto afetam todos os gerenciadores igualmente, porque todos instalam do mesmo registro. Não é falha do bun.

2. "O aube vai reescrever tudo." Não. Ele lê e escreve o lockfile existente (yarn/npm/pnpm/bun) e cai por cima do projeto sem migração. É drop-in, não substituição do ecossistema. (O item #1 da newsletter, o "Executor", esse sim não é gerenciador de pacotes — é um "MCP-of-MCPs" pra agentes de IA. Assunto totalmente diferente.)

2. O que virou a chave de "seguro" em 2026: Shai-Hulud

O tema de segurança do ano no JS não é qual gerenciador você usa — é o worm Shai-Hulud no registro do npm. Foram várias ondas:

  • Set/2025 — primeira onda: phishing num maintainer → 1.300+ versões comprometidas, ~2 bilhões de downloads/mês.
  • Nov/2025 — Shai-Hulud V2 ("The Second Coming"): 700+ pacotes, 27.000 repos maliciosos, ~14.000 segredos vazados.
  • Mai/2026 — "Mini Shai-Hulud": 170+ pacotes npm.
  • Ago/2026 — nova onda: 1.280+ pacotes, 2+ bilhões de instalações/mês, roubando segredos (GitHub, npm, AWS, SSH, VPN…) durante o install.

A indústria convergiu para duas defesas, e as duas são independentes do gerenciador:

  • Bloquear scripts de post-install (o vetor que o worm usa pra rodar durante o install).
  • Quarentena por idade de release (minimum release age): não instalar uma versão publicada há menos de N dias, dando tempo pra comunidade pegar o pacote comprometido antes de ele cair no seu node_modules.
O ponto que decide a resposta: vocês já fazem tudo isso — no Yarn

O .yarnrc.yml do app-webclient já tem:

  • enableScripts: false — scripts de post-install desligados. É exatamente o vetor principal do Shai-Hulud, bloqueado.
  • YARN_NPM_MINIMAL_AGE_GATE via CI (age-gate nativo do Yarn Berry 4.10+), lendo da mesma variável de organização que o Renovate usa.
  • Renovate com minimumReleaseAge (7 dias) + Dependabot + o check de idade no CI, e o yarn.lock commitado.

Ou seja: as "features de segurança" que o aube anuncia como diferencial (minimum release age + jail de scripts) vocês já têm, num tool maduro. Migrar pra ganhar segurança seria trocar de ferramenta pra ter o que já está no lugar.

4. aube em detalhe — por que é interessante, e por que não agora

O que tem de bom

  • Autor confiável. jdx é o criador do mise (ex-rtx), ferramenta muito adotada e respeitada. Não é um projeto de fim de semana.
  • Escrito em Rust, com pipeline de install nativo e paralelo — daí a velocidade (warm install ~8x mais rápido que pnpm nos benchmarks dele).
  • Drop-in de verdade: lê/escreve o lockfile que você já tem, sem migração. Segue o padrão do uv no Python.
  • Segurança opinada por default: minimum release age + "jails" pra scripts de post-install.

Por que não vale a troca hoje

  • Maturidade. Lançado em 2026, v2.2.x. No Hacker News a leitura é "promissor, mas ainda não recomendado pra produção" — testadores relatam abrir bug de compatibilidade com pnpm diariamente (consertam rápido, mas ainda há lacunas) e ~30% mais lento que pnpm em monorepos grandes.
  • Ganho zero de segurança pra vocês. O que ele vende, vocês já têm no Yarn.
  • Frontend de cliente não é lugar de experimento. É whitelabel, buildado no Netlify, com Angular CLI. Um gerenciador de 3 meses aí é risco sem retorno.

5. Se um dia quiserem mexer (não agora)

Se em algum momento a dor for disco/velocidade (não segurança), a troca de menor risco e maior maturidade é pnpm — não o aube (novo demais) nem o bun (que arrasta o runtime junto). Mas isso é "nice to have", não urgente: o Yarn 4 entrega bem e está integrado.

O que de fato move o ponteiro de segurança (e vocês já fazem) independe do gerenciador: enableScripts: false, age-gate, lockfile commitado, Renovate/Dependabot. Manter isso é o que importa — em qualquer gerenciador.

Deixe o aube na lista de observação. Vale reavaliar daqui a ~6–12 meses: se ele amadurecer como o uv amadureceu no Python, aí sim a conversa muda.
