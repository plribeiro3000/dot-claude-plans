SOURCE 1: martinfowler.com/bliki/ParallelChange.html
CANONICAL TERM: Parallel Change (also: Expand and Contract)
=============================================================

Verbatim (fetched 2026-06-24):
"Parallel change, also known as expand and contract, is a pattern to implement
backward-incompatible changes to an interface in a safe manner, by breaking the
change into three distinct phases: expand, migrate, and contract."

"During the migrate phase you update all clients using the old version to the new
version. This can be done incrementally and, in the case of external clients,
this will be the longest phase."

"Once all usages have been migrated to the new version, you perform the contract
phase to remove the old version and change the interface so that it only supports
the new version."

"Most database refactorings follow the parallel change pattern, where the migrate
phase is the transition period between the original and the new schema, until all
database access code has been updated to work with the new schema."

=============================================================

CANONICAL TERM: Deploy vs Release distinction
=============================================================

Verbatim (fetched 2026-06-24):
"Deploy: the process of building, testing, and rolling out changes to your production
software. Deploying should happen very often, ideally several times a day."

"Release: the process of changing user experience in a meaningful way. This might mean
anything from adding functionality to adding entire product lines."

"Feature flags are a scalpel, where deploys are a chainsaw. Both complement each other,
and both have their place."

"Deploying software is a terrible, horrible, no good, very bad way to go about the process
of changing user-facing code."

"you should wrap any large, user-visible behavior changes behind a feature flag, so you can
release that code by flipping a flag."

SOURCE 5: martinfowler.com/bliki/CanaryRelease.html
CANONICAL TERM: Canary Release
=============================================================

Verbatim (fetched 2026-06-24):
"a technique to reduce the risk of introducing a new software version in production by
slowly rolling out the change to a small subset of users before rolling it out to the
entire infrastructure."

"As you gain more confidence in the new version, you can start releasing it to more
servers in your infrastructure and routing more users to it."

"it is preferable to avoid conflating these two concerns: while canary releases are a
good way to detect problems and regressions, A/B testing is a way to test a hypothesis
using variant implementations."

"[canary release is] an application of ParallelChange, where the migrate phase lasts
until all the users have been routed to the new version."

SOURCE 7: github.com/ankane/strong_migrations (README)
TOOL: strong_migrations gem (Rails)
=============================================================

Verbatim (fetched 2026-06-24):
Mission: "Catch unsafe migrations in development"

"An operation is classified as dangerous if it either 'Blocks reads or writes for more
than a few seconds (after a lock is acquired)' or 'Has a good chance of causing application
errors.'"

Multi-step approach for rename:
"Create a new column, Write to both columns, Backfill data from the old column to the
new column, Move reads from the old column to the new column, Stop writing to the old
column, Drop the old column."

For zero-downtime column removal:
"Active Record caches attributes, which causes problems when removing columns. Be sure
to ignore the column" by adding `self.ignored_columns += ["name"]` before removing.

SOURCE 12: getunleash.io/blog/claude-code-unleash-agentic-ai-release-governance
TOPIC: Claude Code + Feature Flag Governance via MCP
=============================================================

Verbatim (fetched 2026-06-24):
"But autonomy without governance is a recipe for instability."

"You can encode your FeatureOps policies in a CLAUDE.md file at the project root.
Claude Code reads this file automatically and applies its guidance."

NOTE: The sentence "Teams define rules in a CLAUDE.md file that Claude Code reads
automatically, specifying which domains require flags and naming conventions." does NOT
appear verbatim in the source. The confirmed verbatim is the sentence above.

The MCP server provides five key functions:
1. evaluate_change - Analyzes code modifications to determine flag necessity
2. detect_flag - Checks for existing flags to prevent duplication
3. create_flag - Generates new flags with proper naming conventions
4. wrap_change - Produces framework-specific flag guard code
5. cleanup_flag - Guides safe flag removal after rollout completion

SOURCE 13: developertoolkit.ai/en/claude-code/lessons/migrations/
TOPIC: Claude Code migration handling
=============================================================

Verbatim (fetched 2026-06-24):
For zero-downtime column operations, Claude Code implements expand-contract in three phases:
1. Pre-deploy: "add the new column as nullable, add a database trigger to keep both
   columns in sync, backfill existing data"
2. Deploy: Update application code to write to both columns while reading from the new one
3. Post-deploy: Remove the trigger, enforce NOT NULL constraints, drop the legacy column

"Without it [the trigger], rows written by old-code instances would have an empty first_name."

For large tables:
"tracks progress (the last processed ID) so it can resume from where it left off if
interrupted, rather than starting over."

=============================================================

Verbatim (fetched 2026-06-24):

"don't let your developers write non-idempotent jobs that are unsafe to interrupt"
