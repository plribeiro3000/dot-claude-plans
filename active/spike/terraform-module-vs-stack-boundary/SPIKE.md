# SPIKE: Module vs Stack — where a Terraform resource belongs, and how to enforce it

**Status**: Research complete — policy proposal awaiting engineer decision
**Date**: 2026-08-04
**Question**: When a resource has to exist for a component to work, does it belong in the child module or in the stack's `main.tf`? What does the community say, and which parts of the answer can a mechanical hook enforce?

---

## Context

The 4Shark terraform repository is approaching PR #1000 and covers nearly the whole infrastructure: four `app` stacks, five `integrator` stacks, one `onboarding`, one `setup`, plus networking, dns, monitoring, identity, vpn and mongodb. Its module library holds 34 modules.

The trigger for this spike is a concrete failure pattern observed while adding an administrative PgBouncer user to every connection pooler:

1. First attempt — the same username and password were used for every environment. One credential covering four stacks: a leak in any environment is a leak in all of them.
2. Second attempt — a per-environment credential, but generated by a `random_password` resource declared in each stack's `main.tf`. Correct blast radius, wrong location: the resource that the component cannot work without was left to the caller to remember.

The pooler is mandatory for the app to work (ADR-009) and the admin user is mandatory for a zero-downtime database cutover (`PAUSE` / `RESUME` / `RECONNECT`). Anything in that class must arrive with the module, not be reassembled per stack.

---

## Findings

### F1 — HashiCorp names three criteria for what goes inside a module: encapsulation, privileges, volatility

The first one answers this spike's question directly.

> "Group infrastructure that is always deployed together."

> "Restrict modules to privilege boundaries."

> "Separate long-lived infrastructure from short-lived."

> "Modules should be opinionated and designed to do one thing well. If a module's function or purpose is hard to explain, the module is probably too complex."

The admin user, the random password and the secret that carries it are deployed on every single pooler deployment, sit inside the same privilege boundary as the pooler, and share the pooler's lifetime. All three criteria point the same way: inside the module.

- URL fetched: https://developer.hashicorp.com/terraform/tutorials/modules/pattern-module-creation
- Quote substring confirmed under the "Encapsulation" / "Privileges" / "Volatility" / "Scope" headings

### F2 — The root module is the *composition* point, and dependency inversion applies to shared dependencies — not to a component's own internals

> "module _receives_ its dependencies from the root module, which can therefore connect the same modules in different ways to produce different results"

> "in most cases we strongly recommend keeping the module tree flat, with only one level of child modules"

This is the finding most likely to be misread as contradicting F1. It is not. What the root module injects is the set of things the child module *cannot know* — the VPC it lands in, the subnets, the ARN of a secret owned by another stack, the security group of a peer component. A resource whose only reason to exist is the module's own operation is not a dependency; it is an internal.

The practical discriminator: a dependency is something that exists whether or not this module is instantiated. The pooler's admin password does not exist without the pooler.

- URL fetched: https://developer.hashicorp.com/terraform/language/modules/develop/composition
- Quote substring confirmed in the "Dependency Inversion" and module-tree sections

### F3 — Root modules are meant to stay thin instantiation layers

> "Don't include more than 100 resources (and ideally only a few dozen) in a single state."

> "split the Terraform configuration for the service into two top-level directories: a `modules` directory that contains the actual configuration for the service, and an `environments` directory"

Google's phrasing puts the *actual configuration* in modules and leaves environment directories as the place where modules are instantiated with per-environment values. 4Shark's `<project>-<environment>` stacks are exactly that `environments` layer under a different name.

- URL fetched: https://docs.cloud.google.com/docs/terraform/best-practices/root-modules
- Quote substring confirmed in the resource-count and directory-structure sections

### F4 — The secrets rule the community states explicitly: no default, and auto-generation is the named exception

Cloud Posse's Terraform best practices state:

> "All `variable` inputs for secrets must never define a `default` value."

> "Use `sensitive = true` to mark all secret variables as sensitive."

and record the one exception as a secret that "is optional and will be auto-generated if left `null` or empty".

The first attempt in this repository's own history is the failure this rule prevents: a shared default credential is precisely a secret whose value came from somewhere other than the environment it protects. The exception describes the shape being proposed here — the module generates the credential itself.

- URL fetched: https://docs.cloudposse.com/best-practices/terraform/
- Quote substring confirmed in the secrets/variables section

### F5 — Terraform ≥1.11 has a first-class way to keep a generated secret out of state

> "Write-only arguments let you securely pass temporary values to Terraform's managed resources during an operation without persisting those values to state or plan files."

> "Terraform does not store write-only arguments in state files"

Paired with the `random_password` **ephemeral** resource, a module can generate a credential and write it into Secrets Manager (`secret_string_wo` + `secret_string_wo_version`) with the value appearing in neither plan nor state. This is relevant because moving credential generation into the module concentrates more secrets inside the module's blast radius — write-only arguments are what keep that concentration from also concentrating state exposure.

- URL fetched: https://developer.hashicorp.com/terraform/language/manage-sensitive-data/write-only
- Quote substring confirmed in the introductory definition

### F6 — 4Shark already made this exact decision once, at a coarser grain: ADR-009

ADR-009 rejected "documentation + review discipline" and "a thin wrapper module", and chose a domain module that instantiates the pooler unconditionally:

> "created **unconditionally**: no `count`, no toggle, no `enabled` variable. There is no way to instantiate `modules/app` without the pooler."

> "No pooler = no cluster = the module cannot be instantiated. The rule is enforced by the type system of the configuration, not by a reviewer's memory."

> "A rule that isn't enforced by construction gets forgotten"

The policy this spike proposes is the same principle applied one level down: what ADR-009 did for *the pooler inside the app*, the policy does for *everything the pooler needs in order to work*.

- File read: `~/Projects/4Shark/terraform/docs/adr/ADR-009-mandatory-connection-pooler.md:41`, `:43`, `:56`

### F7 — The repository already states the blast-radius rule in a code comment, but only for one resource

`app-shared-001/connection_pooler.tf:9-10`:

> "One key per stack, so a leak or a rotation reaches this environment and stops there."

The principle is written down, applies to the Datadog API key, and is repeated verbatim in each of the four app stacks. Nothing generalizes it and nothing enforces it — which is how the shared-credential attempt got written in the first place.

The same rule already exists at the global level in `~/.claude/CLAUDE.md` § Third-Party Service Key Standard: *"One key per entity — the entity IS the blast radius"*. Its scope there is third-party service keys (Datadog, Rollbar). Terraform-generated credentials are the uncovered half.

- Files read: `~/Projects/4Shark/terraform/app-shared-001/connection_pooler.tf:9`

### F8 — Measured: 22 resource declarations are duplicated identically across all four app stacks

Grouping every `resource "<type>" "<name>"` declaration in `app-shared-001`, `app-beta-001`, `app-demo-001` and `app-atento-001` by (type, local name):

| Count | Examples |
|---|---|
| 22 declarations appear in **all four** stacks | `datadog_api_key.connection_pooler`, `aws_secretsmanager_secret.connection_pooler_userlist`, `aws_secretsmanager_secret.connection_pooler_datadog_api_key`, `aws_iam_role.ecs_task_execution`, `aws_iam_user.deploy`, `aws_ssm_parameter.secrets`, `aws_route53_record.database_primary`, `aws_ecs_cluster_capacity_providers.this` |
| 1 in three stacks | `aws_cloudwatch_log_group.rds_postgresql` |
| 2 in two stacks | `aws_security_group.opensearch`, `aws_route53_record.database_replica` |
| the remainder in one stack each | per-environment security groups, subnet groups, the maqnelson outbound zone associations |

This is the mechanically decidable signal. A resource declared with the same type and the same local name in every stack of a family is, by definition, not environment-specific — it is the module's content sitting outside the module. The single-stack entries are the legitimate residue: environment-specific wiring, cross-region peering, one client's outbound zone association.

Note that `random_password` already appears once in a stack today (`random_password.mongo_readonly`), so any hard block on that resource type in stacks has one pre-existing occurrence to resolve first.

- Source data: `/tmp/tf_stack_resource_counts_20260804.txt` (generated from a grep over the four stacks' `.tf` files)

### F9 — Conftest can evaluate policy against `.tf` source files, not only against a plan

Conftest ships an `hcl2` parser, invoked as `conftest test <file>.tf -i hcl2` (`conftest parse <file>.tf -i hcl2` shows the parsed shape). This matters because the rule being enforced here — *where* a resource is declared — is a property of the source layout, and disappears once `terraform plan` flattens modules into a single resource graph.

Known limitation: the HCL parser does not resolve variable interpolation, so a policy can see that `resource "random_password" "x"` exists in a given file but cannot evaluate what `var.something` expands to. That is sufficient for the rules proposed below, all of which are structural.

This finding comes from search-result summaries and a GitHub issue title, not from a fetched official parser page (the `conftest.dev/parsers/` URL returns 404). Treat the exact flag spelling as **to be verified by running it** before writing any policy against it.

- Sources: https://www.conftest.dev/ , https://github.com/open-policy-agent/conftest/issues/3 (search summaries; **not individually fetched** — the invocation must be confirmed locally)

## Synthesis — proposed 4Shark policy

**Name**: *Mandatory by Construction* — the generalization of ADR-009 from "the pooler inside the app" to "everything a component needs in order to work".

### The rule

> A resource the component cannot function without is created **by the module**, unconditionally, with no variable that lets a caller omit it, share it, or supply it. The stack supplies only what the module cannot know: its network, its neighbours, and the values that genuinely differ per environment.

### The three-question test

Applied to any resource, before choosing a file:

1. **Does the component work without it?** No → module. This is the strongest signal and it decides most cases. A pooler with no admin user cannot be cut over; a cluster with no task-execution role cannot start a task.
2. **Is it the same in every environment that uses this component, apart from names and values?** Yes → module (with the differing part as a variable — never the resource itself).
3. **Does it connect the component to something outside itself** — a VPC, another stack's output, another client's zone, a peering? Yes → stack, injected as an input (F2, dependency inversion).

### The credential corollary

A module that needs a credential **generates** it — it never declares a `variable` for the value:

- `random_password` (or its ephemeral variant) lives inside the module, so each instantiation produces a distinct credential and two environments *cannot* share one, because there is no input through which sharing could be expressed.
- The module writes the credential to Secrets Manager and outputs the **ARN**, never the value. With Terraform ≥1.11, `secret_string_wo` + the ephemeral `random_password` keeps the value out of plan and state (F5).
- The only credential-shaped variables a module accepts are `*_secret_arn` inputs — references to secrets owned elsewhere, which is exactly what `modules/connection_pooler` already does for the Datadog API key and stats password (`variables.tf:153-161`).
- A secret variable with a `default` is forbidden outright (F4).

This corollary is what makes the first failure structurally impossible rather than merely discouraged: the shared credential was expressible because a variable existed to express it.

### What legitimately stays in the stack

Naming the residue matters as much as naming the rule, otherwise the policy reads as "everything goes in the module" and gets ignored the first time it is inconvenient:

- Provider configuration (modules declare `required_providers`, never `provider` blocks).
- Cross-stack wiring: `data.terraform_remote_state`, `aws_ssm_parameter` lookups, remote outputs.
- Environment-unique topology: the maqnelson cross-region zone association, per-environment peerings, one-off security-group rules.
- Values a module cannot derive: environment name, sizing, image digests, CIDRs.
- Secrets **owned out of band** whose lifecycle is deliberately outside Terraform (the userlist secret populated by hand is a current, documented example).

## Mechanical enforcement — three candidate layers

Each layer is independently adoptable. They are listed cheapest-first, and the third is the only one that blocks.

### Layer A — context injection at write time (no block)

A `PreToolUse` hook on `Edit|Write|MultiEdit` matching `*.tf` **outside** `modules/` injects the three-question test before the write. Same shape as `inject-terraform-context.sh` and `inject-migration-conventions-on-write.sh`, and appropriate for the same reason: "is this resource mandatory for the component?" is judgment, not a fixed fact, so it cannot be blocked without false positives.

Cost: one script, no false-positive risk, no legacy cleanup. Reaches the moment the decision is actually made.

### Layer B — duplication detector (flag, not block)

A script that groups every `resource "<type>" "<name>"` across the stacks of a family and reports any declaration appearing in ≥2 stacks as a module candidate. F8 shows it would fire on 25 declarations today, including every connection-pooler secret.

Two viable wirings: a `PostToolUse` flag like `check-bulk-delete.sh` (fires only on the file just written), or a CI check on the PR diff. The CI form is stronger — it sees the whole repository rather than one file — but it reports pre-existing duplication on unrelated PRs until the backlog is cleared, so it needs either a baseline file or a diff-only mode.

Cost: mechanically decidable, zero judgment, but it has a real backlog behind it (the 22 four-way duplicates).

### Layer C — hard blocks on two narrow shapes

Both are structural and decidable from the file path plus a regex:

1. **`resource "random_password" / "random_string" / "random_id"` declared in a stack file** — a generated credential in a stack is the failure mode this spike started from. One pre-existing occurrence (`random_password.mongo_readonly`) must be moved or explicitly exempted first.
2. **A `variable` whose name matches a secret shape (`password`, `secret`, `token`, `key`) without the `_arn` suffix, declared in `modules/*/variables.tf`** — a module asking for a credential value instead of generating it. Worth confirming against the current module set before enabling, since a legitimate `*_secret_arn` exception already exists and other shapes may too.

Cost: highest confidence, highest risk of blocking a legitimate case, and each block needs the legacy occurrence resolved before it can be turned on.

### Where the policy text would live

`~/.claude/docs/TERRAFORM-POLICY.md` already reaches every terraform command through `inject-terraform-context.sh`, so a summary section there plus a `**See**:` pointer to a new `TERRAFORM-MODULE-BOUNDARY.md` follows the existing loading model. The decision itself is ADR-shaped and belongs in the terraform repository as `docs/adr/ADR-011-mandatory-by-construction.md`, since it generalizes ADR-009 and lives with the code it governs.

## Open questions for the engineer

1. **Which layers to adopt.** A alone is the cheap, no-backlog option; A+B gives the measurable signal; A+B+C makes the specific failure impossible.
2. **The Layer B backlog.** 22 declarations duplicated across four app stacks is a real migration into `modules/app`. It can be done incrementally (one resource group per PR, `moved{}` blocks, the same state-surgery path ADR-009's rollout used), or the detector can be baselined so it only reports new duplication.
3. **Write-only arguments.** Adopting `secret_string_wo` + ephemeral `random_password` requires Terraform ≥1.11 and touches every module that generates a credential. Worth doing as part of this policy, or a separate follow-up?
4. **Whether the policy binds beyond `app`.** The integrator, onboarding and setup stacks were not measured for duplication in this spike — only the four app stacks were.
